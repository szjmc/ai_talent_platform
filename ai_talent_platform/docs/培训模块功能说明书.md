# 智能培训赋能模块 · 功能说明书

> 模块：智能培训赋能 Agent（需求 2.4，标签 `[Dify组] [P1]`）
> 版本：2026-11-05
> 本文只描述**已经实现并有测试覆盖**的能力；未实现的明确列在第七节，不与功能混写。

---

## 一、一句话定位

输入一名人才的**能力短板**，输出一份**能落地执行的培训计划**：学什么课、第几周学、学多久、怎么盯进度、怎么考核、考过之后怎么回流复测。

不是"推荐几门课"，是一条从诊断到复测的完整闭环。

---

## 二、能力全景

| 节点 | 做什么 | 输入 | 输出 | 失败时的行为 |
| --- | --- | --- | --- | --- |
| 1 短板诊断 | 去掉已达标项，算缺口、优先级、预估学时 | 测评分 / 显式短板 + 可选岗位 ID | 排序后的短板清单 | 无可用分数 → 400 并说明缺什么 |
| 2 方案排期 | 按优先级把学时排进周次，每周限容量 | 短板清单 + 周期 + 周容量 | 周次骨架 | 装不下 → **400 并给出建议周数**，绝不偷偷压缩 |
| 3 课程匹配 | 把"维度"落成课程库里的真实课程 | 周次骨架 + 课程库 + 已学课程 | 带 course_id 的课表 | 库里没课 → 降级为外部学习建议，**绝不编造课名** |
| 4 落库推送 | 计划、课表、初始记录入库，发事件 | 课表 | plan_id + 完成率 | 人才不存在 → 404 |
| 5 进度跟踪 | 单调递增校验、反作弊、落后判定 | 上报的进度与学时 | 状态 + 预警级别 | 越权/越界 → 422，不回退 |
| 6 考核复测 | 80 分判定，通过回流测评 | 考核分数 | 通过结论 + 事件 | 人才与计划不符 → 422 |

---

## 三、逐节点规则（可核对的数字）

### 节点 1 · 短板诊断

- **缺口** = 目标分 − 当前分；`delta <= 0` 视为已达标，**直接不排课**（个性化的第一层）。
- **优先级**：缺口 ≥ 20 分 → P0；≥ 8 分 → P1；其余 P2。**权重 ≥ 0.25 的岗位关键维度，无论缺口多少一律抬到 P0。**
- **预估学时**：`round(缺口 / 4) + 2`，再夹在 **3 ~ 8 小时**之间。
- **排序**：先 P0→P2，同档内按 `缺口 × 权重` 降序（既补得多、又是岗位看重的排前面）。
- **标准的三个来源**，按优先级取：调用方显式传入 > 岗位能力模型 > 默认值（目标分 80、权重 0.2）。
- **岗位模型解析顺序**：显式 `position_id` → 人才现职位名称去 `positions` 精确匹配 → 拿不到就回退默认值。
- 来源会写进 `requirement_source`（`explicit` / `position_model` / `default`），并记录岗位 ID 与模型版本。

### 节点 2 · 方案排期

- 每周默认上限 **8 学时**，单个学习单元最长 **4 学时**（避免一门课压满一周）。
- 容量 = 周期 × 周容量；需求量超过容量时抛 `CapacityExceeded`，接口返回 **400**，文案直接给建议周数：
  `短板总学时 16.0h 超出周期容量 2.0h，建议延长至 8 周或下调目标分`。
- 排期分两条路：先算规则基线（**顺带完成容量校验**），再尝试 LLM 优化。
- LLM 排期必须过 `legal_skeleton` 校验：维度必须在短板清单内、周次在范围内、学时为正、每周不超上限。**任意一条不满足就回退规则基线**，不会把非法排期落库。
- 无 LLM 凭据时**不发请求**（避免 3 次重试 + 跨模型降级链的 5~8 秒等待），直接用规则基线，`generated_by=rule`。
- 同周同维度会合并，避免课表碎成十几条。

### 节点 3 · 课程匹配

- 每门课按四层筛选：**维度一致 → 未学过且未被占用 → 层级贴合（允许偏离目标 1 档）→ 学时优先**。
- 同一维度跨多周时**复用同一门课**，不重复占课。
- 库里没有该维度的课 → 该单元 `is_platform=false`，给出 `external_suggestion`（"建议公开课/外部机构，需 HR 线下采购"），**不编造课程名**。
- 输出 `library_rate` = 平台课程占比；整份计划全是外部建议时不会谎报 100%。

### 节点 4 · 落库与推送

- 一次写三处：`training_plans`（计划，含 `created_by_ai` 与来源测评 ID）、`plan_courses`（课表，含**周次** `sort` 与 `require_pass`）、`learning_records`（每门课初始化 0 进度）。
- `auto_push=true` → 状态 `ongoing`，否则 `draft`。
- 方案说明优先由 LLM 生成，失败或过短则用规则文案（模板：人数、维度、周数、学时、考核周与及格线）。
- 发 `training.plan.created` 事件（通知 / 审计交给订阅方，失败不影响主流程）。
- **全部达标时不是报错**：返回 `status=finished`、`items=[]`、文案"各维度均已达标，本期无需安排培训"。

### 节点 5 · 进度跟踪

- **进度只能升不能降**：提交值小于已存值直接 **422**，并把当前值写进提示。
- **归属双重校验**：人才必须是计划所属人才；课程必须在该计划的课表里。任一不符 422（前者曾导致 500，后者曾静默写脏数据）。
- **反作弊**：按进度应付学时 = 课程学时 × 进度%，实际学时低于应付的 **30%** 则标记 `suspicious=true`（只标记、不阻断，留人工判断）。
- **落后判定**：期望学时 = 总学时 × 时间进度；落后比例 ≥ **40%** 判"HR预警"，≥ **20%** 判"提醒"，否则"正常"；学满则"已按期完成"。
- 预警同时产出事件：`training.lag.alert` / `training.lag.remind`，带落后比例与应完成/实际学时。
- `lag-scan` 是给定时任务的入口：扫全部进行中计划，**单条算失败不影响整体**，返回 `scanned / reminded / warned / alerts`。
- 独立成接口而不是塞进业务流程：可重入、可手工补扫、可单独测。

### 节点 6 · 考核复测

- 及格线 **80 分**；未传分数视为"未提交考核"，`passed=null`。
- 通过 → 发 `training.retest.required`（建议 2 周后复测，携带维度清单），计划状态收为 `finished`。
- 不通过 → 发 `training.plan.adjust`（建议延长 2 周补强），计划状态回到 `ongoing`，`need_human=true`。
- 不传 `course_id` 视为**整计划考核**，成绩会写到该计划下每门课——否则通过率的分母永远是 0。
- **完成率 ≠ 通过率**：学满 100% 只写 `status=completed`，**绝不写 `passed=true`**。通过结论只能由本节点产生，通过率分母只含"已出结论"的记录。

## 四、接口清单（16 个）

| 方法 | 路径 | 作用 | 权限 |
| --- | --- | --- | --- |
| POST | `/trainings/plans/generate` | 生成方案（节点 1~4）。支持 `draft`（只存不下发）/ `replace_existing`（替换在途计划） | `training:manage` |
| GET | `/trainings/plans` | 计划分页（批量算完成率，无 N+1） | `training:read` |
| GET | `/trainings/plans/{id}` | 计划详情（课表 + 溯源字段） | `training:read` |
| GET | `/trainings/plans/{id}/progress` | 进度统计与预警（纯查询，不发事件） | `training:read` |
| POST | `/trainings/plans/{id}/score` | 提交考核。带 `course_id` 只判该课；不带则整计划结课。已结课需 `force=true` 才能改分 | `training:manage` / `training:report`（仅本人） |
| GET | `/trainings/stats/pass-rate` | 通过率（整体 + 按课程） | `training:read` |
| POST | `/trainings/records` | 写回学习进度 | `training:manage` / `training:report`（仅本人） |
| POST | `/trainings/lag-scan` | 滞后扫描（定时入口），同时写站内信 | `training:manage` |
| GET | `/trainings/notifications` | 我的站内信分页（未读数一并返回） | `training:read` |
| POST | `/trainings/notifications/read-all` | 全部标记已读 | `training:read` |
| POST | `/trainings/notifications/{id}/read` | 单条标记已读 | `training:read` |
| GET | `/trainings/courses` | 课程分页（关键词/分类/层级/上架） | `training:read` |
| POST | `/trainings/courses` | 新建课程（重名拒绝） | `training:manage` |
| PUT | `/trainings/courses/{id}` | 更新课程（改名同样查重） | `training:manage` |
| DELETE | `/trainings/courses/{id}` | 下架课程（软删） | `training:manage` |
| POST | `/trainings/recommend` | 只推荐课程、不建计划 | `training:read` |

错误码约定：参数/业务校验失败 **422**（code 1001）、业务规则不满足 **400**（code 1002）、资源不存在 **404**（code 3001）、**状态冲突 409**（code 3003，如重复计划、已结课后重复打分）。

**两个易被追问的返回值语义**

1. **全维度已达标**时 `POST /plans/generate` 返回 `id: null` + `no_training_needed: true`（HTTP 201）。
   早期用 `id: 0` 表示"无需培训"，前端会把它当真实计划去查详情，一查就是 404。
2. **同一人才已有进行中的计划**时，再次生成返回 **409** 并给出旧计划 id 与处置建议；
   确认要替换则重发并带 `replace_existing: true`，旧计划置为 `cancelled`（不是删掉，保留追溯）。

## 五、数据模型（5 张表）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `courses` | `category` `level` `duration_hours` `skill_tags` `is_active` | `category` **必须与能力维度名一字不差**（排课靠它匹配） |
| `training_plans` | `talent_id` `status` `created_by_ai` `source_assessment_id` `start_date` `end_date` | 状态：`draft` / `ongoing` / `finished` / `cancelled` |
| `plan_courses` | `plan_id` `course_id` `sort`(**周次**) `require_pass` | 唯一键 `(plan_id, course_id)` |
| `learning_records` | `plan_id` `course_id` `progress` `study_minutes` `status` `score` `passed` `examined_at` `suspicious` | 唯一键 `(plan_id, course_id, talent_id)`；`plan_id`/`course_id` 为 **NOT NULL** |
| `training_notifications` | `plan_id` `talent_id` `type` `level` `notify_date` `is_read` | 唯一键 `(plan_id, type, notify_date)`，保证同一计划同一天同类通知只推一次 |

`learning_records.plan_id / course_id` 为什么必须 NOT NULL：唯一键是 `(plan_id, course_id, talent_id)`，
而 **MySQL 唯一索引对 NULL 不生效**（`NULL != NULL`）。允许 NULL 时，同一人才对同一门课可以插入任意多条
"孤儿记录"，按 `plan_id + course_id` 取值会抛 `MultipleResultsFound`，完成率与通过率全部失真。

课程下架走**软删**：历史计划的课表与通过率统计都引用 `course_id`，硬删会留下空洞。

完成率按**学时加权**计算：`Σ(progress × 课程学时) / 总学时`，不是"课程数简单平均"。
否则 1 门 2 学时的小课学完、1 门 8 学时的大课没开始，也会显示 50% 完成。

## 六、对外事件（5 个）

| 事件 | 触发点 | 携带 |
| --- | --- | --- |
| `training.plan_created` | 计划落库并下发后 | plan_id、talent_id、计划名、总学时、渠道 |
| `training.retest.required` | 考核通过 | plan_id、talent_id、维度清单 |
| `training.plan.adjust` | 考核不通过 | plan_id、分数、建议（延长 2 周） |
| `training.lag.remind` | 落后 ≥ 20% | plan_id、talent_id、落后比例 |
| `training.lag.alert` | 落后 ≥ 40% | plan_id、talent_id、应完成/实际学时 |

发事件而不是直接调别的模块：降耦、HR 可关、重启后可由 outbox 补偿（当前为进程内实现，见第七节）。

**事件不会"空转"**：这 5 类事件在 `EventBus.ALL_EVENTS` 全部登记，并由
`notification_service.register_training_notification_subscribers()` 在应用启动时挂上订阅者，
同步落一条 `training_notifications` 站内信（学员端可见）。早期只登记了 `plan_created` 一个、
且没有订阅者，发出去的事件全部被静默丢弃——功能"看起来做了"，实际什么都没发生。

## 七、明确的边界（当前不做的事）

写清楚"不做什么"，比多列三条功能更可信：

1. **不编造课程**：课程实体只能来自课程库。库里没有就降级成外部建议，宁可方案不完整，也不给学员一个查不到的课名。
2. **不静默丢学时**：容量不足直接报错并给建议周数，不把学时偷偷塞进最后一周。
3. **不模糊匹配维度**：课程分类差一个字就是匹配不上，**不会凭相似度挂课**（错课比没课更误导人）。降级时会打 `WARNING` 日志，带上"疑似应为"与库内现有分类，供运营核对。
4. **不把学完当考过**：完成率与通过率严格分开。
5. **不改别人的表**：读测评、岗位、人才只走三个只读门面（`AssessmentGapReader` / `PositionRequirementReader` / `TalentExistenceReader`），不写对方任何数据。
6. **不做的事**：复测消费（下游自动建复测单）、计划调整落地接口、培训 ROI 分析，当前均未实现（见验收报告第五节）。

> 已补齐（原列在"不做"里）：**学员端自助上报**已实现——`training:report` 权限 + `users.talent_id` 绑定，
> 员工只能给自己写进度/打分（越权写别人的 `talent_id` 返回 422），主管与 HR 不受此限。

## 八、跨模块交接契约

| 上游 | 给什么 | 缺了怎么办 |
| --- | --- | --- |
| 测评 Agent | `gaps`: `dimension` / `current` / `required` / `weight` | `current` 必填；`required`、`weight` 可缺，由岗位模型或默认值补 |
| 岗位模型 | `dimensions`（JSON：`{"维度": 80}` 或 `{"维度": {"required": 80, "weight": 0.25}}`） | 解析失败/未维护 → 回退默认标准，并标注 `requirement_source=default` |
| 人才档案 | `talent_id` 必须真实存在；`current_position` 用于反查岗位 | 不存在 → 404，并提示先建档 |

下游：`training.retest.required` 应被测评 Agent 消费，自动建复测单并回写分数，形成"测评 → 培训 → 复测"的闭环。**当前消费方未实现，闭环断在最后一步**，这是本模块最需要补齐的一环。

## 九、可用性设计（答辩常被问的三点）

1. **零 Key 也能跑通**：没有模型凭据时直接走规则排期，不卡在重试链上，演示环境不会因为没配 Key 就白屏。
2. **降级可视**：`generated_by`（rule / llm）、`summary_source`、`requirement_source` 三个字段，前端能解释"这份方案是模型排的还是规则排的、标准来自岗位模型还是默认值"。
3. **每个阈值都可调**：优先级分档、周容量、单块上限、及格线、预警线都提在 `training_logic.py` 顶部，改一处全局生效，不用翻业务代码。
