# 远端环境培训模块数据为空——原因与初始化方案

标签：[Dify组] [P1]（远端演示环境数据初始化排障）

编写日期：2026-11-06
适用对象：培训模块负责人、部署执行人

---

## 一、现象

组员在远端环境（`121.43.198.251`）查看培训模块，数据库记录为 0，页面能打开但无任何课程与计划。

## 二、实测结论

连接 `121.43.198.251:3306`（MySQL 8.0.27，库 `ai_talent_platform`）核查：

| 表名 | 列数 | 行数 | AUTO_INCREMENT | 建表时间 | UPDATE_TIME |
|---|---|---|---|---|---|
| `courses` | 17 | 0 | 1 | 2026-11-04 04:09:40 | NULL |
| `training_plans` | 16 | 0 | 1 | 2026-11-04 04:10:16 | NULL |
| `plan_courses` | 6 | 0 | — | 2026-11-04 04:10:38 | NULL |
| `learning_records` | 18 | 0 | 1 | 2026-11-04 04:10:40 | NULL |

同一库内其他模块的表均在正常写入，可作对照：

| 表名 | 行数 | AUTO_INCREMENT | UPDATE_TIME |
|---|---|---|---|
| `users` | 13 | 76 | 2026-11-06 04:09 |
| `files` | 146 | 195 | 2026-11-06 06:03 |
| `talents` | 62 | 65 | 2026-11-05 16:35 |

**判定：**

1. 表**已建好**，且四张表的列与当前代码 ORM 模型**完全一致**（17/16/6/18 列，无缺列、无多余列）。
2. 自增值为 1 且 `UPDATE_TIME` 为 `NULL`，说明这四张表**自建表后从未被写入过任何一行**——不是数据被删除，也不是账号权限不足。
3. 因此问题是**数据未初始化**，而非表结构缺失。

## 三、根因

培训模块的数据由两个脚本产生，二者此前仅在本机（`127.0.0.1`）执行过，远端从未执行：

| 脚本 | 产出 | 本机实测 |
|---|---|---|
| `scripts/seed_training_courses.py` | `courses` 19 门课 / 8 个能力维度 | 19 门，与脚本 COURSES 定义一一对应 |
| `scripts/demo_training.py` | `training_plans` 4 个计划 + `plan_courses` 13 条 + `learning_records` 39 条 | 与脚本运行结果一致 |

应用启动时的 `lifespan → init_db() → create_all()` **只建表、不灌数据**（这是有意设计，业务数据不应由应用自动写入）。因此远端即使完整启动过一次（表已建出），培训相关表仍然是空的。

此外需注意：**课程库为空时培训模块不会报错**，只会静默降级——节点 3「课程智能匹配」不满足「课程 100% 来自课程库」的条件，整份方案会退化为「外部学习方向建议」，节点 2 排出的课表无课程。表现即"页面能用但什么都没有"。

## 四、初始化方案

### 前置检查（必须先做）

1. **确认远端部署的代码包含培训模块**

   本分支 `lz_agent` 的合并提交（`e1916de`、`8a1175f`）需先推送并部署。若远端仍运行原 `lz` 分支，`trainings` 前缀为 501 占位路由，此时即使灌入数据前端也调不到接口。

   ```bash
   git log --oneline -3          # 应包含 e1916de / 8a1175f
   git push origin lz_agent
   ```

2. **确认目标库连接信息**

   远端 `.env` 使用：

   ```
   DB_HOST=121.43.198.251
   DB_PORT=3306
   DB_USER=root
   DB_NAME=ai_talent_platform
   DB_CHARSET=utf8mb4
   ```

   本机 `.env` 为 `127.0.0.1` / 密码 `123456`，**两者不是同一个库**，库名相同极易混淆。

### 方式 A：在服务器上执行（推荐）

```bash
cd <项目部署目录>
git pull origin lz_agent

python scripts/init_db.py                  # 幂等：只补建缺失的表，不删不改已有表
python scripts/seed_training_courses.py    # 19 门课程
python scripts/demo_training.py            # 可选：生成演示计划与学习记录
```

### 方式 B：本地直连远端执行（不改服务器）

脚本通过 `pydantic-settings` 读取配置，**环境变量优先级高于 `.env`**，因此可临时覆盖而不修改任何配置文件。

Git Bash：

```bash
cd "C:/Users/Windows/Desktop/项目文件/ai-digital-talent-platform"

DB_HOST=121.43.198.251 DB_PORT=3306 DB_USER=root DB_PASSWORD=root123456 \
DB_NAME=ai_talent_platform \
python scripts/seed_training_courses.py
```

Windows CMD：

```bat
set DB_HOST=121.43.198.251
set DB_PASSWORD=root123456
python scripts\seed_training_courses.py
```

> 执行前请二次确认 `DB_NAME=ai_talent_platform`，避免命令拼写错误指向其他库。

### 幂等性说明

- `seed_training_courses.py`：按 `title` 判断，已存在则更新 `category / level / duration_hours / skill_tags`，不重复插入，可安全反复执行。
- `demo_training.py`：先删除**该演示人才（手机号 `13900001086`）名下**的历史计划再重建，不影响其他人；若远端无此人才会新建一条「张伟」，已确认远端当前无同手机号、无同名记录，不会误挂到已有人员。

## 六、禁止事项

**不要直接用 `mysqldump` 把本机培训数据整体搬到远端。**

原因：`talent_id` 在两库中指向不同的人。

| 主键 | 本机 | 远端 |
|---|---|---|
| `talents.id = 2` | 张伟 | 李欣怡 |

本机 4 个计划的 `talent_id` 全部为 2。直接导入会把计划挂到远端的「李欣怡」名下，数据存在但归属错误。

如需迁移历史数据，正确做法是在远端新建对应人才后重新映射 `talent_id`，或直接执行 `demo_training.py` 重新生成。

## 七、其他发现（建议同步架构组）

1. **远端库表数量为 33，代码 ORM 模型为 29。** 多出的 `matching_reviews`、`matching_review_events`、`question_bank_questions` 三张表，当前代码中**无任何模型定义**，推测由其他分支的 `create_all` 或手工 DDL 产生。该库被多个分支共用，结构已出现漂移，建议明确唯一的建表与迁移入口，避免长期累积。

2. **安全性**：远端 MySQL 对公网开放 3306 且使用 `root` + 弱口令，建议限制来源 IP 白名单，或改用受限账号供应用连接。

3. **对外端口**：远端 8000 端口从外网不可达，前端联调需确认实际暴露方式（反向代理或未部署）。
