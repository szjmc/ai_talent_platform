# 周期报告接口迭代方案（周报 / 月报 / 年报）

> 状态：✅ 已实现并验证通过（2026-11-05）
> 负责模块：`app/ai/agents/analytics_agent.py` + `app/ai/workflows/analysis_workflow.py` + `app/routers/agent_router.py`

---

## 一、结论先行

周期报告**不是新功能，而是"换个问法 + 换个叙事框架"**。

你的 Agent 已经具备完整能力链：

```
取数(Vanna) → 出图(chart_builder) → 风险规则(detect_risks) → 第一次LLM拼prompt → 第二次LLM业务推理(report_meta)
```

周报 / 月报 / 年报只需要在**最后一环（拼 prompt 那一步）**注入不同的"叙事模板"，让 LLM 把同样的数据按「周总结 / 月趋势 / 年复盘」的口径重新组织，就能产出三种报告。

**因此方案核心就一句话：新增 1 个接口 + 1 套模板常量，复用全部现有能力，不落库、不造轮子。**

---

## 二、三种报告的本质差异

| 维度 | 周报 | 月报 | 年报 |
|------|------|------|------|
| 时间跨度 | 最近 7 天 | 最近 30 天 | 最近 365 天 |
| 分析重点 | 即时异常、本周动态 | 环比变化、月度趋势 | 年度复盘、结构演变 |
| 对比口径 | 本周 vs 上周 | 本月 vs 上月 | 本年 vs 去年 |
| 结论风格 | "本周发生了什么，下周注意什么" | "这个月比上个月好/差在哪" | "这一年人才结构发生了什么变化" |
| 建议颗粒度 | 即时行动（P0 为主） | 短期改进（P0+P1） | 战略调整（P1 为主 + 长期规划） |

**关键认知**：差异主要在"问法"和"叙事"，不在"取数逻辑"。取数清单 `QUERY_GROUP_MAP` 完全复用，不需要为周期报告单独写查询。

## 三、接口设计

### 新增接口

```
POST /agents/report/period
```

### 请求体

```json
{
  "report_type": "weekly",        // 必填：weekly / monthly / yearly
  "question": "生成一份人才决策周报"   // 可选，默认走标准盘点问句
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `report_type` | str | 是 | `weekly`(周报) / `monthly`(月报) / `yearly`(年报) |
| `question` | str | 否 | 自定义问句，不填则用模板默认问句 |
| `conversation_id` | str | 否 | 与 `/agents/chat` 一致，支持追问 |

### 响应体

与 `/agents/chat` 完全同构（复用 `parse_output`），额外多两个字段：

```json
{
  "answered": true,
  "report_type": "weekly",
  "period_label": "2026年第45周",        // 计算出的周期标签，如「2026年第45周」「2026年11月」「2026年度」
  "conclusions": [...],
  "suggestions": {...},
  "risk_list": [...],
  "charts": [...],
  // ... 其余字段与 /agents/chat 一致
}
```

### 三个周期标签的计算规则

| report_type | period_label 规则 | 示例 |
|-------------|------------------|------|
| weekly | `{年份}年第{ISO周号}周` | 2026年第45周 |
| monthly | `{年份}年{月份}月` | 2026年11月 |
| yearly | `{年份}年度` | 2026年度 |

> 计算用 Python 标准库 `datetime` / `date` 的 `isocalendar()`，**不手工算时间戳**，避免算错年份。

## 五、叙事模板设计（核心增量）

这是本次迭代**唯一真正新增的逻辑**，其余全是复用。模板长这样：

```python
PERIOD_REPORT_TEMPLATE = {
    "weekly": {
        "label": "周报",
        "time_span": "最近 7 天",
        "compare": "本周与上周",
        "focus": "即时异常、本周动态、下周关注",
        "prompt_guide": (
            "请以「周报」口径组织这份报告：\n"
            "1. 关注本周的即时变化与异常，而非长期趋势；\n"
            "2. 结论要回答「本周发生了什么、下周该注意什么」；\n"
            "3. 建议以 P0 即时行动为主，颗粒度要细、可立刻执行。"
        ),
    },
    "monthly": {
        "label": "月报",
        "time_span": "最近 30 天",
        "compare": "本月与上月",
        "focus": "环比变化、月度趋势",
        "prompt_guide": (
            "请以「月报」口径组织这份报告：\n"
            "1. 强调本月与上月的环比变化，指出好转或恶化的指标；\n"
            "2. 结论要回答「这个月比上个月好/差在哪」；\n"
            "3. 建议分 P0（本周落地）与 P1（本月推进）两级。"
        ),
    },
    "yearly": {
        "label": "年报",
        "time_span": "最近 365 天",
        "compare": "本年与去年",
        "focus": "年度复盘、结构演变、战略调整",
        "prompt_guide": (
            "请以「年报」口径组织这份报告：\n"
            "1. 关注年度结构演变与长期趋势，而非单点异常；\n"
            "2. 结论要回答「这一年人才结构发生了什么变化」；\n"
            "3. 建议以战略调整为主，偏长期规划，可淡化即时行动。"
        ),
    },
}
```

**注入方式**：`build_insight_prompt` 在现有 prompt 基础上，把 `prompt_guide` 插到角色约束之后、数据块之前，让 LLM 按周期口径重写 conclusions / suggestions / group_summaries。**数据结构不变，输出 schema 不变**，因此 `parse_output` 一行都不用改。

## 六、为什么不做"落库 + 跨期对比"

你选了"暂不落库，只做单次模板"，这里说明清楚取舍，方便以后反悔再补：

| 能力 | 不落库（本次方案） | 落库（后续可加） |
|------|------|------|
| 周报/月报/年报单次生成 | ✅ 支持 | ✅ 支持 |
| 月报对比"过去 4 周数据" | ❌ 做不到 | ✅ 支持 |
| 年报对比"12 个月趋势" | ❌ 做不到 | ✅ 支持 |
| 定时自动生成 | ✅ 可用 automation | ✅ 更完整 |

**为什么现阶段不落库是对的**：

1. 测试数据快照只有 2025-10 / 2025-11 两个月，跨期对比没有数据支撑（`analysis_workflow.py` 里规则 3.4 也是因为这个才挂起的）；
2. 落库要新增表结构 + 写 DB 层 + 考虑权限，改动面大、风险高，与"课程演示优先"的定位不符；
3. 单次模板已能完整演示周/月/年报的"叙事差异"，是性价比最高的做法。

等接入真实数据（多月份快照）后，再补落库 + 跨期对比，那时"月报/年报"才真正有历史数据可对比。
