一条总原则：所有接口都套同一个信封 {code, message, data, trace_id}。判断成功看 code === 200，不要看 HTTP 状态码——两者绝大多数时候一致，但 501 占位和部分业务错误会让你误判。

任意接口 · 成功响应

字段类型说明

1.2 鉴权：怎么带、带多久、哪些不用带

登录拿 access_token，之后每个请求加一个头：

HTTP Header
Authorization: Bearer <access_token>
项实测值说明
令牌形态JWT（长字符串，约 300 字符）无状态，服务重启不失效（沙箱是内存态 token，重启就失效——这是两套服务最大的行为差异）
有效期expires_in: 86400（24 小时）登录时传 remember_me: true 延长到 7 天
刷新POST /auth/refresh用 refresh_token 换新的 access_token，前端应在 401 时自动重试一次
退出POST /auth/logoutJWT 无状态，服务端不会让 token 立即失效，需前端自己丢弃

无需鉴权的接口（可直接访问，用于启动自检和登录）：

POST /api/v1/auth/login · POST /api/v1/auth/refresh · POST /api/v1/auth/register · GET /health · GET /health/ready · GET /api/v1/system/info · GET /api/v1/system/skills · 以及 8 个 501 占位接口。

1.3 分页：三件套 + 五个返回字段

凡返回列表且可能很长的接口（/users、/organizations、/matchings），统一用这套参数：

参数类型默认说明

3认证模块（6 个）

这组接口解决两件事：证明你是谁（login / refresh / me）、管理你自己的凭据（logout / register / change-password）。业务接口全部依赖这里拿到的 token，所以它是所有链路的第 0 步。

坑 2：别把 refresh_token 当 access_token 用。两者都是长 JWT，肉眼几乎分不出，但签名用途不同，混用会 401。

POST/api/v1/auth/refresh 已实现无需鉴权

干什么：access_token 快过期或已过期时，用 refresh_token 换一套新的，避免让用户重新登录。

谁在用 前端请求拦截器前置 手里有未过期的 refresh_token副作用 无

输入（Body · JSON）

字段类型必填说明
refresh_tokenstring是登录时返回的那个，不要加 Bearer 前缀

输出（data）

结构同 TokenResponse：新的 access_token / refresh_token / token_type / expires_in。不含 user——要刷新用户信息请另调 /auth/me。

推荐的拦截器写法：遇到 401 且 code=2001 时，先判断本地有没有 refresh_token；有就调一次 refresh 并重放原请求，失败再跳登录页。只重试一次，避免死循环。

谁在用 应用初始化、路由守卫前置 有效的 access_token副作用 无（纯读）

POST/api/v1/auth/logout 已实现需鉴权

干什么：语义上的退出。当前实现不会在服务端作废 token，只是返回成功让前端清本地存储。

5人岗匹配（5 个）

这是整个系统的核心产出。五个接口分两类：算（run / explain）和查（列表、按岗位、按人才）。算的会写库、可能调外部模型；查的全是纯读。

先记住这条铁律，能避免 80% 的困惑：匹配不是"打分排名"，是四态硬条件判定 + 分数排序。四种状态里只有 FAIL 会被淘汰，UNKNOWN（档案缺数据）和 NEEDS_REVIEW（需人工看）都会保留在榜单里。所以"榜单有 4 个人，但候选人 5 个"是正常现象。

四态语义（贯穿全部 5 个接口）

状态含义是否淘汰前端怎么展示
PASS硬条件满足，有证据支撑否绿色"符合"
FAIL明确不满足（如要求本科、实际大专）是红色"不符合"，并给原因
UNKNOWN人才档案里没这项数据，无法判定否灰色"待补充"，提示去补档案
NEEDS_REVIEW数据有歧义或冲突，需人工判断否黄色"需复核"，进人工队列

为什么 UNKNOWN 不淘汰？因为"档案没写"不等于"不具备"。淘汰它等于把潜在合格者误杀，这在招聘场景里代价很高。这是我实测确认过的设计，也是这套系统与普通关键词筛选的本质区别。

7.0 先理解 level 与 path

每个部门存两个冗余字段，用来避免递归查询：

字段含义实测值
level层级深度，根为 1，子级 +1研发部 level=1
path从根到自己的 ID 路径串，用于前缀匹配查子孙类似 /1；子部门是 /1/5

所以移动部门时必须重算自己 + 所有子孙的 level 和 path，这就是 PATCH /move 存在的原因——不能直接改 parent_id。

11数据结构字典

接口的"输入输出"说到底就是这几个对象在传递。这节是给要写代码的人看的——字段名和嵌套关系必须精确，错一个字母就是 null。

11.1 JobProfileParsed（岗位画像 · 最核心）

字段类型必填说明与读法
job_titlestring是岗位名称。唯一必填字段
responsibilitiesstring[]否岗位职责原文列表
required_conditionsConditionItem[]否必要条件条目（text / normalized / source_span / confidence）。
实测常为空数组，别指望从这里拿判定值
preferred_conditionsConditionItem[]否优先条件条目，只加分不淘汰
required_skillsstring[]否必备技能（硬性）。这是硬过滤真正用的字段
preferred_skillsstring[]否优先技能（软性加分）
min_educationstring/null否最低学历。null = JD 未提及，禁止补默认值
min_work_yearsint/null否最低年限。null 同理，不要当 0 处理——当 0 会让所有没写年限的候选人都 PASS
locationstring/null否工作地点
salary_rangestring/null否薪资范围原文，如 "25k-35k"，未结构化
missing_fieldsstring[]否缺失字段名，由 Python 计算（不是模型产出）
conflictsstring[]否冲突描述，同样 Python 计算
review_requiredboolean否是否需 HR 人工确认。实测恒为 true
sourcestring否产出来源：dify / llm / manual
prompt_versionstring否提示词版本，如 rule-v1，用于回溯与 A/B

三条铁律：① null 表示"JD 没写"，不等于 0 或空字符串，判定时对应 UNKNOWN 而不是 FAIL；② 硬条件判定看扁平字段，不是 required_conditions；③ missing_fields / conflicts 是计算结果，不要回传给 confirm（虽然 schema 允许，但会污染数据）。

11.2 HardConditionResult（单项四态判定）

字段类型说明
itemstring条件名：min_education / min_work_years / required_skills
requiredany岗位要求值（原值，可能是字符串 / 数字 / 数组）

这一条是整套系统的"审计最小单元"：任何一个分数，都能顺着 hard_results → evidence_id 追回到"哪条 JD 要求、哪份档案的哪个字段、为什么这么判"。这就是"可解释"的落地方式，不是一段 AI 话术。

12谁调谁：三条链路

接口按业务串起来才有意义。这三条是系统里真实存在的调用序列，覆盖 90% 的使用场景。

12.1 场景 A：新岗位上线（HR 主流程）

登录→ jd/parse→ HR 修订画像→ profile/confirm→ matchings/run→ positions/{id}→ explain
  1. POST /auth/login → 拿 token，之后每个请求都带上
  2. POST /positions/1/jd/parse → 传 JD 原文，拿回画像草稿（不落库）
  3. （前端）HR 在页面上修订 → 改 min_work_years、加 required_skills 等
  4. GET /positions/1/profile → 拿当前 version（这步不能省，否则 confirm 会被乐观锁拒）
  5. POST /positions/1/profile/confirm → 带 profile + expected_version，画像生效，版本 +1
  6. POST /matchings/run → 跑批，拿 batch_id + 榜单 + stats
  7. GET /matchings/positions/1 → 下次进页面用这个读（不重算）
  8. POST /matchings/explain → 点开某个候选人时按需调

顺序不能颠倒的点：第 4 步在第 5 步之前（乐观锁）；第 5 步在第 6 步之前（未确认画像 run 会 400）。这两条是最常见的"卡住"原因。

12.2 场景 B：HR 日常看人（高频，不走 run）

登录→ matchings/positions/{id}→ 点候选人 → explain

关键：不要每次进页面都调 run。run 会写库、会重算、可能要调模型。日常浏览一律用 by-position 读缓存结果，只有用户明确点"重新匹配"才 run。

12.3 场景 C：这个人还适合什么岗位

matchings/talents/{id}→ 前端按 position_id 去重取最高分→ explain（指定 position_id）

注意这个接口返回的是历史多条（同一人同一岗位多批会有多条），前端必须自己聚合。

12.4 系统内部：一次 run 里发生了什么

  1. 取画像：读最新已确认的 position_requirements，没有就 400
  2. 召回：talent_ids 为空时按岗位条件查 talents；Milvus 未启用 → recall_mode=sql_fallback
  3. 硬条件判定：对 min_education / min_work_years / required_skills 逐项判四态，每项生成 evidence_id
  4. 淘汰：仅 FAIL 进 excluded，其余全部保留
  5. 打分：四维（skill / quality / education / experience）加权成 score
  6. 排序编号：按分数倒序，写 rank（从 1 开始）
  7. 解释：with_explanation=true 时调 Dify → 失败降级 LLM → 再失败走规则；false 时直接规则
  8. 落库：写 matching_records，一个批次 ID 串起所有候选人
