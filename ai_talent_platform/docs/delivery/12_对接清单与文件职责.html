04Dify 工作流怎么配合

代码里的调用规格已经固定（app/adapters/dify/dify_adapter.py）， Dify 侧只要按这个契约交付，我这边不用改代码。

两个工作流的分工

工作流 key干什么入参变量名出参必须能被谁解析
job_profile_extraction 自然语言 JD → 结构化岗位信息（学历/年限/必备技能/优先技能/地点/薪资） jd_text（string） JobProfileParsed（Pydantic）
match_explanation 结构化证据包 → 自然语言解释（summary / highlights / gaps / 面试建议） evidence_pack（string，JSON 文本） MatchExplanation（Pydantic）

实际发出的请求长这样

// POST {DIFY_BASE_URL}/workflows/run
{
  "inputs": { "jd_text": "岗位职责：… 任职要求：本科及以上，3 年经验，熟悉 Python…" },
  "response_mode": "blocking",   // 同步等待，超时可重试
  "user": "ai-talent-platform"
}
// 期望返回：outputs 里是一个能被 JobProfileParsed 直接校验通过的 JSON

向 Dify 管理员索取 5 样（缺一不可）

  • ① DIFY_BASE_URL —— 完整到 /v1，例如 https://dify.example.com/v1
  • ② DIFY_API_KEY —— 两个工作流是否共用同一个 Key（也支持按工作流分别配置）
  • ③ 工作流标识 —— 是走「工作流 API」还是「应用 API」，对应的 ID 或名称
  • ④ 入参变量名 —— 必须就是 jd_text / evidence_pack； 若对方用了别的名字，我改一行映射即可，但要提前知道
  • ⑤ 一次真实 curl 的返回体样例 —— 这个最重要：我要拿它验证 _normalize 能否吃掉

联调节奏（建议按这个顺序，别跳步）

步骤动作验收标准
1对方发布工作流，给你 curl能返回 200
2你把返回体贴给我我用 JobProfileParsed / MatchExplanation 离线校验通过
3填 .env 的 DIFY_API_KEY 并重启 8010响应里 channel 从 rule_fallback 变 dify
4跑一次完整匹配 + 解释解释里每条结论都有 evidence_ids，且没有编造的 ID

三条不能让的红线（已在代码里固定）

  • Dify 只做「表达」不做「判定」：硬条件、分数、排序全部由 Python 规则计算， Dify 拿不到也不会拿到打分权。
  • Dify 不能绕过 Service 直接访问数据库：它只接收证据包、返回文字。
  • 失败必须降级且如实标注：Dify 超时/结构不合法 → 自动回落规则解释， source 标 rule_fallback，绝不伪装成 Dify 输出。
失败时会看到什么：不会 500，也不会空响应。你会看到 channel=rule_fallback，以及 errors 里一条人话原因（如「Dify 返回结构不合法」）。 这条降级链已有 6 个用例覆盖（超时、5xx、4xx、非 JSON、缺字段、编造证据）。

05LLM 现状：不是缺端口，是模型选型

这一节是我在整理文档时实测发现的，和之前的结论不同，所以单独列出来。

实测事实：本机 11434 端口是通的，Ollama v0.40.13 在跑， 已装两个模型：qwen3:0.6b（对话，751M）和 bge-m3（向量，1.1G）。 项目本身也有 app/adapters/llm/ollama_adapter.py，且 explanation_service._llm_configured() 明确写了「Ollama 本地模型不需要 Key」。

但直接切过去会失败，原因很具体

测试参数结果
默认调用num_predict=400 content 为空 400 token 全被思考过程吃掉
关闭思考think=false 正常输出 但只有 200 token 就结束，内容偏短
看适配器代码ollama_adapter.chat 不传 think payload 只有 model/messages/stream/options， think 是顶层字段，透过 **kwargs 塞不进 options
结论：不是网络问题，是 qwen3 系列的 thinking 机制 + 适配器没暴露该参数。 0.6B 的模型对着「证据包 JSON」这种长输入，可靠性和字段遵循度也不够，做演示可以，做生产不行。

两个可选方案（都不影响现在的规则兜底）

方案动作成本效果
A. 换非 thinking 模型（推荐） ollama pull qwen2.5:1.5b（约 1GB）或 qwen2.5:7b， 再把 .env 改成 LLM_PROVIDER=ollama、LLM_MODEL=qwen2.5:1.5b、 LLM_BASE_URL=http://127.0.0.1:11434 零代码改动，只改配置 + 下载模型 能出中文解释；7b 质量明显更好，但需要更多显存
B. 给适配器加 think 开关 在 ollama_adapter.chat 的 payload 里加 "think": False（1 行 + 1 个用例） 要改代码，需你批准 qwen3 也能用，但 0.6B 仍偏弱
我没有动配置。按我们之前的约定，改 .env 或代码前要先经过你确认。 要试的话告我选 A 还是 B，我改完会用真实请求验证 channel 是否真的变成 llm_fallback。

五层校验：ID 是否存在、术语是否越界、有没有拿「缺失」证明「具备」、 结论是否引用有效证据、断言是否超出证据范围。不合格的结论剔除并记原因。

把证据包写成自然语言。外部通道不可用时回落规则模板，source 如实标注。 输出含 highlights、gaps、pending_verification、rejected_claims。

整批写入 matching_records，连同画像版本、召回方式、四态明细、解释、统计一起留痕。 页面刷新后从库里还原，结果与执行时逐字一致。

services/matching_service.pyrepositories/matching_repository.py

阶段 5 的分叉：四态怎么走

PASS
条件满足
正常进入打分排序
FAIL
唯一可淘汰态
进 excluded，必带原因
UNKNOWN
档案缺失
保留 + 该维度按 85% 计
NEEDS_REVIEW
年限为 0 等存疑
保留，转人工复核
这条是业务红线，也是我最容易被质疑的设计： 「不确定」不等于「不合格」。所以 UNKNOWN 和 NEEDS_REVIEW 一律保留，宁可让人多看一眼， 也不能因为档案没填就把人筛掉 —— 之前正是这个 bug 把一位档案空白但条件不错的候选人误杀了。

三个关键设计（值得单独记住）

  • 两处刻意不落库：JD 解析只是草稿（POST /jd/parse 不写库），解释只是即时计算 （POST /explain 不写库）。只有「确认画像」和「跑批结果」写库。
  • 跑批钉住画像版本：requirement_version 随结果一起存，半年后能回答「当时按哪版要求筛的」。
  • 所有判断都能回到字段：每条结论挂 evidence_ids，能反查到人才的原始字段值； 编造或越界的结论会被校验器剔除并记录原因。

08闭环缺口与建议顺序

把「一次真实招聘」拆成 9 个环节后，匹配算法本身是完整的，缺的是「人怎么进来、结论怎么出去」。

优先级缺口影响工作量是否越界
P0岗位 CRUD 新岗位只能手写 SQLRepository 已有通用 CRUD，补 Service + 路由 + 用例 岗位模块，需授权
P0人才写入接口 新候选人进不来，演示只能靠脚本造数同上 人才模块，需授权
P0人工决策回写 跑完匹配不是业务结论，只是一张分表 2 个可空列 + 1 个 PATCH 接口不越界，但需 DDL
P1JD 原文留档 画像无法回溯依据确认时多存一个字段需岗位模块配合
P1批次对比视图 调参前后谁升谁降看不出来stats.weights 已留痕，只差一个对比接口不越界
P1结果导出 CSV HR 没法拿给用人部门一个接口 + 一次查询不越界
P2Milvus 向量召回 召回覆盖面窄（只靠标签）运维部署 + 打开开关不越界
P3前端页面 目前只有接口，没有界面需前端介入他人负责
最小闭环路线：P0 的三项做完， 就能跑通「新建岗位 → 录入 JD → 确认画像 → 新候选人入库 → 跑匹配 → 给出人工结论」。 其中岗位 CRUD 和人才写入属于别人负责的模块，我按边界没有动 —— 需要你点头我才开始。
