〇、一页速览（给赶时间的同学）

平台侧代码已 100% 就绪（适配器、降级链、五层校验、测试全部完成并标注「暂定·待联调」）。Dify 组要做的事：

  1. 按本文档的字段契约，在 Dify 上创建 2 个工作流：job_profile_extraction（JD 解析）、match_explanation（匹配解释）。
  2. 提交一份契约确认单（见第 6 节 6 问），逐项书面确认。
  3. 交付 Base URL + 两个应用的 API Key（放入平台 .env 即通）。
  4. 与平台联调，验收判据：解析响应 source="dify"、解释响应 channel="dify"，且所有 evidence_ids 通过五层校验。

最重要的一条向量维度式的一次性契约冻结：inputs 变量名、outputs 字段名一经联调确认即冻结，后续改名 = 双方同步改代码 + 全量回归。

一、背景与调用关系

岗位 Agent 匹配链路中有两个环节依赖 Dify 工作流，其余环节（召回、四态判定、四维打分、证据构建、五层校验、落库）均由平台自身完成：

JD 原文→ ① Dify：JD 解析
job_profile_extraction→ 画像确认（HR）→ 召回 → 判定 → 打分 → 证据包→ ② Dify：匹配解释
match_explanation→ 五层校验 → 展示
分工铁律（需求文档已明确）：Dify 只做语义提取与自然语言表达，不做业务判定、不算分。 四态判定（FAIL/NEEDS_REVIEW/UNKNOWN/PASS）、0-100 打分、证据 ID 生成全部在平台侧。 Dify 输出只是「素材」，平台会做白名单过滤与五层校验，校验不过的结论会被剔除并记录到 rejected_claims。

降级链（平台侧已实现，Dify 无需关心，但需要理解为什么契约必须严格）

场景JD 解析实际通道解释实际通道响应标识
Dify 正常Dify 工作流Dify 工作流source="dify" / channel="dify"
Dify 失败（超时/5xx/结构错误）规则提取兜底LLM 降级 → 规则兜底rule_fallback / llm_fallback
未配置 Key（本地开发常态）直接跳过 Dify直接跳过 Dify同上，不发无意义请求

平台不会伪装降级结果，所以 source="dify" 出现即代表真实联通。联调成功的唯一判据就是这两个字段出现真实值。

项目约定说明

鉴权Authorization: Bearer {DIFY_API_KEY}每个工作流应用一个独立 API Key（共 2 个）

平台侧对响应的解析规则（Dify 侧输出必须满足其一）

# 形态 A：单字段输出（Dify Cloud 默认）—— outputs.result 为 JSON 字符串或对象
{ "workflow_finished": true, "outputs": { "result": "{...业务 JSON...}" } }

# 形态 B：多字段输出（自建版常见）—— outputs 本身就是业务对象
{ "workflow_finished": true, "outputs": { "job_title": "...", "required_skills": [...] } }

# 平台解析顺序：outputs.result（可 JSON.parse 则解析）→ 直接取 outputs 本体
# 两种形态都支持，但必须在契约确认单中声明用哪种，避免联调时互相猜

三、工作流 ①：job_profile_extraction（JD 解析）

3.1 功能定义

输入 JD 自然语言文本，输出结构化岗位信息。只做语义提取，不做判定（不判断候选人、不算分、不筛选）。HR 后续会在画像确认页人工核对，Dify 提取错误可被人工修正，但缺字段会导致 HR 反工，所以「字段宁全勿缺、拿不准就留空并说明」。

3.2 inputs（变量名必须完全一致）

变量名类型必填说明
jd_textstring是JD 全文（平台保证 ≥ 20 字，上限约 2 万字）。可能含「岗位职责 / 任职要求 / 加分项」等段落标记，也可能完全无结构

注：岗位名称提示（job_title）当前不传入 Dify。若 Dify 侧希望增加此可选输入变量，请在确认单中提出，平台侧加一行即可。

3.3 outputs（业务 JSON 字段契约）

平台按白名单 + 别名映射接收（兼容下表「别名」列的写法，但推荐直接用首选名，别名命中会降低可读性）：

字段（首选名）类型必填约束 / 说明兼容别名
job_titlestring必须缺失时平台直接报错要求人工补录，画像无法构建title
responsibilitiesstring[]建议岗位职责短句列表，缺失记入 missing_fieldsduties
required_conditionsstring[]条件必填必备硬条件短句；当 required_skills 已抽出时可为空，两者都空才记缺失must_have / conditions
preferred_conditionsstring[]否优先/加分条件短句nice_to_have
required_skillsstring[]建议必备技能（技能名，非句子）skills / must_skills
preferred_skillsstring[]否优先技能plus_skills
min_educationstring建议枚举值：不限 / 大专 / 本科 / 硕士 / 博士（平台按这 5 档归一化；写「全日制本科」等变体会进 conflicts 待人工确认）education
min_work_yearsint | null建议最低工作年限，0~50；「应届」→ 0，未提 → nullexperience_years
locationstring否工作地点—
salary_rangestring否薪资范围原文（如「25k-35k」）—
prompt_versionstring建议Dify 侧提示词版本号（≤20 字符），平台原样入库用于审计与 prompt 迭代追踪—
三条硬性约束（违反会直接产生业务问题）： ① job_title 缺失 = 平台报错，画像构建失败； ② 同一技能不得同时出现在 required_skills 与 preferred_skills（平台会记入 conflicts 强制人工确认）； ③ 禁止补值——JD 里没写的字段就留空/null，不要猜「本科以上默认」「默认 3 年经验」，猜错比缺失更糟（缺失只是提示，补值会错误淘汰候选人）。

四、工作流 ②：match_explanation（匹配解释）

4.1 功能定义

输入一份结构化证据包（岗位 × 人才 × 判定 × 打分 × 证据清单），输出自然语言匹配解释。只做表达，不算分、不改判定。平台拿到输出后执行五层证据校验：每条结论必须引用真实存在的 evidence_ids，无依据结论一律剔除并记录。

4.2 inputs

变量名类型必填说明
evidence_packstring(JSON) 或 object是完整证据包 JSON。建议 Dify 侧输入变量用 string 类型、内部自行解析；若 Dify 支持 object 类型直传请确认后声明（两种平台都能给，确认单里定一种）

4.3 证据包结构（MatchEvidencePack，平台侧 pydantic 模型，逐字段给出）

字段类型说明
position_id / talent_idint岗位 / 人才 ID
requirement_versionint本次使用的岗位画像版本号
job_profile_summaryobject岗位画像（结构与 3.3 节 outputs 相同，另含 missing_fields / conflicts）
hard_resultslist四态判定明细，每条含：condition（条件名）、status（FAIL / NEEDS_REVIEW / UNKNOWN / PASS）、reason、evidence_ids
dimension_scoresobject四维分数：skill / experience / education / quality（0-100）
data_completenessfloat档案完整度 0~1。低于 0.7 时请 Dify 在解释里显式提示「结论建立在缺失数据上」（missing 类证据见下）
evidenceslist证据清单，每条：evidence_id（格式 EVID-{position_id}-{talent_id}-{seq}）、claim（证据支撑的结论短句）、source_table / source_field / source_value（来源表/字段/原值）、requirement_ref（对应岗位要求字段）、evidence_type（fact 档案原值 / derived 代码推导 / missing 依据缺失）

4.4 outputs（解释 JSON 契约 —— 五层校验会逐条核对）

字段类型约束
summarystring综合匹配结论，1~1000 字，必填非空
highlightslist<claim>核心优势，每条 = {text, evidence_ids, claim_type}
gapslist<claim>能力差距，同上
riskslist<claim>潜在风险，同上
interview_suggestionsstring[]建议面试问题（无需挂证据）
pending_verificationstring[]待人工核实事项（含 UNKNOWN 项、与缺失数据相关的说明）
prompt_versionstring解释提示词版本（≤20 字符）

其中单条 claim 的结构：

字段类型约束
textstring1~500 字
evidence_idsstring[]至少 1 条，且必须逐字存在于入参 evidences 的 evidence_id 中——校验器逐 ID 比对，编造 / 拼错的 ID 会导致整条结论被剔除并记入 rejected_claims
claim_typeenumfact（档案事实陈述）/ inference（推断，前端会标注「需人工复核」）
证据使用规则（校验器的剔除原因即来源，请写进 Dify 侧 prompt）： ① evidence_type="missing" 的证据（如「档案无技能字段」）只能用于说明「信息缺失、无法判断」，拿它证明人才具备某能力 = missing_evidence_misuse，整条剔除； ② 结论不得超出证据 claim 与 source_value 的语义范围（越界 = term_out_of_scope 剔除）； ③ 结论不得与 hard_results 中 FAIL 判定冲突（冲突 = conflict_with_hard_result 剔除）； ④ 被剔除不是异常，是设计——rejected_claims 越少说明 Dify prompt 质量越高，这是双方共同的迭代指标。

五、非功能性要求

项目要求原因
响应时间P95 ≤ 30s，硬上限 60s平台超时 60s 即降级，跑批场景一次可能串行解释多人，慢会放大
错误码语义401/403 = Key 无效；404 = 路径错；429 = 限流；5xx = 服务异常平台按状态码分类决定重试与降级策略
限流请告知配额（QPS / 日调用量），写入确认单跑批按人才数线性调用，平台侧需要据此做节流
输出稳定性输出必须是可解析的纯 JSON（无 Markdown 围栏、无前后缀文字）。JD 解析若用 LLM 节点，请务必做 JSON 输出约束平台解析失败 = 视为 Dify 失败，直接降级，等于白跑
幂等性同一 inputs 多次调用结果可不同（LLM 特性），但字段结构必须恒定结构漂移 = 降级
日志留痕每条 outputs 必须带 prompt_version平台入库审计，prompt 迭代效果可量化（rejected_claims 率对比）

六、契约确认单（请 Dify 组逐项书面回复）

  1. 部署形态与 Base URL：自建版还是云端版？完整 Base URL（含 /v1 与否）？网络是否与平台服务器互通（内网 / 公网 + 白名单）？
  2. 两个应用的 API Key：每个工作流独立一个 Key，通过安全渠道交付（不要进 git / 群聊，直接给到平台配置人）。
  3. outputs 形态：走「单字段 result」（形态 A）还是「多字段 outputs」（形态 B）？若 result 是字符串，确认它是合法 JSON 文本。
  4. inputs 变量名：确认 jd_text、evidence_pack 两个变量名，以及 evidence_pack 是 string(JSON) 还是 object 直传。
  5. 超时与限流配额：工作流内部模型链路的最大耗时、QPS / 日调用配额。
  6. 错误语义：Dify 侧业务失败（如 LLM 拒答、内容审核拦截）时返回的 HTTP 状态码与响应体格式是什么？平台需要区分「重试能好」和「重试也没用」。
