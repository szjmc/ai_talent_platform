7建议的推进顺序

顺序不是按优先级硬排，而是按依赖关系排——前一批不通，后一批做了也验证不了。

第 1 批本周内

把已有的东西「落地」：提交 + DDL + 密钥

  • 提交 27 项改动，推 lz_agent → 提 MR 到 develop，让别人能 review
  • DBA 审批 5 个可空列的 DDL，测试库同步执行
  • 拿 LLM_API_KEY + DIFY_*（5 样一次问齐），先把 llm_fallback 通道打通
为什么先做这批：零开发量，但决定后面所有联调能不能开始。Dify 契约不定，写再多解释逻辑都是猜。
第 2 批1–2 周

补齐匹配的上游：人才档案 + 文件上传

  • /talents 9 个接口（先做 CRUD + 列表 + 详情，语义检索留到 Milvus 到位后）
  • /files 3 个接口 + 补 file_router.py（现在文件根本不存在）
  • /resumes 上传 + 解析（解析走 JD 解析同一套 Dify 通道，可复用）
为什么：匹配能跑但没有数据入口。人才建档 + 简历导入通了，平台才算「能自助使用」。
第 3 批2–4 周

接真 AI：Milvus + Embedding + RAG

  • Milvus 部署 → init_milvus.py 建集合（dim 与 embedding 对齐 1024）
  • embedding_service → retriever → rag_pipeline 按依赖顺序实现（不能跳）
  • 召回切换：sql_fallback → 向量召回，用同一批数据对比召回质量
  • 顺带打通人才语义检索、简历查重
为什么放第三：Milvus 是知识库、语义检索、查重三个功能的共同前置，一次性解锁三块。
第 4 批可并行

外壳与延伸：Agent 对话、分析问数、双向匹配、前端

  • /agents 5 接口（6 个 Agent 先做 assistant 一个，跑通 SSE 再复制）
  • /analytics：先写 sql_validator，再接 Vanna
  • 双向匹配（复用 MatchingPipeline 反查）+ 储备预警（新表 + 定时任务）
  • 前端：优先「岗位画像确认 → 匹配结果列表 → 匹配解释」三步，够演示
为什么最后：这些都建立在前面数据与 AI 通道之上，早做只会做出「假数据页面」。

8跨组联调必须当面问清的 6 件事

问不清就会各写一套，最后靠人肉对字段。

  1. Dify 契约：两个工作流的 app-id、inputs 变量名与类型、outputs 是单字段 result 还是多字段、超时与错误码怎么区分？
  2. Embedding 维度：向量模型定哪个？dim 定 1024 还是 768？必须与 Milvus collection 一次定死，改一次要重建全库。
  3. 人才档案的数据契约：谁负责写 Talent 表？简历解析结果绑定时，字段冲突以谁为准？
  4. 语义检索的权限过滤：Milvus 的 expr 按部门还是按角色？跨部门检索是否允许？
  5. NL2SQL 的库边界：Vanna 只能查 PgSQL 分析库，还是也能查 MySQL 业务库？能否写？必须只读。
  6. 文件存哪：本地磁盘还是 MinIO？决定了 /files 的下载实现和部署方式（本地盘在多实例下必坏）。
