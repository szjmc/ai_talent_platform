第 2 批3–5 天

Dify 两条工作流联调

  • 向 Dify 组要齐 5 样，冻结契约（inputs / outputs / 错误码 / 超时）
  • 联调 job_profile_extraction → JD 解析出 source=dify
  • 联调 match_explanation → 解释出 channel=dify 且过证据校验
  • 各准备一份「规则 vs Dify」对比记录，交付时能说清 AI 带来的差异
这是你 Agent 的核心 AI 价值所在，也是验收报告里 BLOCKED-1 的解除条件。
第 3 批1–2 周

  • 实现 matching_agent.py：工具直接挂现成的 3 个 matching_skill，prompt 版本化
  • 新增 POST /matchings/reverse（人才找岗位），复用打分内核
  • 顺手给 MatchRunRequest 加可选 weights
外壳不依赖外部服务，可并行推进；双向匹配补齐需求模块五的前半部分。
第 4 批等人到位

向量召回 + 储备预警

  • Milvus 部署 → init_milvus 建集合（dim 与 embedding 定死一致）→ 实现 adapter → 召回切 vector
  • 预警表 + 扫描逻辑，数据源复用匹配批次
  • 上游 talents/resumes 由对应负责人实现后做端到端回归
向量召回质量收益在人才库上规模后才明显，5 人演示库收益为零，不必抢早。

7联调时当面问清的 5 件事（岗位 Agent 版）

  1. Dify 两个工作流的 app-id、inputs 变量名与类型、outputs 是单字段 result 还是多字段、超时与错误码怎么区分？
  2. JD 解析的输入边界：Dify 只做语义提取，判定与补值留在你这边——对方的工作流里有没有偷偷做判定？
  3. Embedding 维度：dim 定 1024 还是 768？必须与 Milvus collection 一次定死，改一次重建全库。
  4. 召回的权限边界：向量召回按部门还是全库？跨部门人才是否允许进入候选池？
  5. 双向匹配的规则归属：岗位满足人才期望（薪资/城市）的硬条件判定，是复用你的四态引擎还是人才组自己写？要提前签字，避免两套口径。
