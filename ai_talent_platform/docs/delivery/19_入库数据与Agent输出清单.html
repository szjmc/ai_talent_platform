19 · 入库数据与 Agent 对接输出清单

岗位人才匹配 Agent（ai-digital-talent-platform）· 基于当前真实代码核验（app/models / app/routers / docs/delivery/18）· 2026-11-05

一、我要入库的数据（我方写入，共 3 张 MySQL 表 + Milvus）

① MySQL：matching_batches（跑批快照表）每次正式跑批写 1 行

文件：app/models/matching.py → MatchingBatch

字段存什么为什么入库
batch_iduuid hex，跑批唯一 ID下游查询、重放、审计的主键入口
position_id / matched_at岗位 ID + 匹配时间支撑"岗位最新结果"查询与储备预警扫描
response完整响应 JSON（含零产出批次）快照可回放；零产出也落库，不伪造明细
request_scope本次输入范围（候选范围、weights 等请求参数）重放历史批次时知道当时的口径

② MySQL：matching_records（人岗匹配明细表）每个候选人 1 行

文件：app/models/matching.py → MatchingRecord · 唯一键 (batch_id, position_id, talent_id)

字段组字段说明
身份与结果batch_id / position_id / talent_id / score / rank逻辑综合分 0-100（Numeric(5,2)）
四维打分dimension_scores（JSON）skill / experience / education / quality 四维分
解释文本highlights / gaps / suggestion / strategy / model_name优势、短板、建议、策略（hard/soft/hybrid）、所用模型
可追溯字段
MATCH-009 新增		requirement_version / recall_mode / hard_results / explanation / stats画像版本、召回方式（vector / sql_fallback 如实记录）、四态判定明细、校验后的解释、跑批统计——支撑"证据可追溯、解释可复核"
操作留痕matched_by / matched_at触发用户、时间（分区键）

注意：岗位/人才用逻辑外键不建物理外键——匹配记录量大、可重建，由 Service 校验存在性。

③ MySQL：reserve_warnings（储备预警表）扫描时写入，幂等 + 自动闭环

文件：app/models/reserve_warning.py · SQL 脚本：docs/sql/2026-11-04_reserve_warnings.sql

预警类型触发条件默认级别
position_no_output岗位最新批次 output = 0（无可用候选人）high
position_reserve_shortage最新批次 PASS 人数低于阈值medium
position_long_vacant开放岗位超过 N 天从未跑批medium

关键设计：同 (warning_type, position_id) 只留一条未解决记录（幂等）；扫描时自动把已不再成立的预警标记 resolved（数据闭环）；逻辑外键，源数据删除后预警仍可追溯。

④ Milvus 向量库间接入库，用于向量召回

链路：岗位画像文本 → embedding（bge-m3, dim=1024）→ Milvus collection，跑批时若向量可用则 recall_mode=vector 召回；Milvus 不可用降级 SQL 召回并如实记录 recall_mode=sql_fallback。相关文件：app/adapters/vector_store/milvus_adapter.py、app/ai/rag/embedding_service.py。

⑤ 明确不落库的接口（只读试算）

  • POST /matchings/reverse 双向匹配（人才找岗位）——只读，不落库
  • POST /matchings/explain 匹配解释——只读重算 + 校验，不落库

理由：试算代价高但属于探索性查询，不产生正式批次；正式结果以 POST /matchings/run 的 batch_id 为准。

二、我依赖谁入库（上游写入、我只读消费）——跟对方要对的"入库清单"

上游他们要入库的数据我拿它做什么
简历解析组talents（技能标签、学历、工作年限、离职状态 status）、resumes 原文与结构化结果四态判定的 actual 实际值、证据 source_table/source_value 的来源；离职人才过滤依赖 talents.status（MATCH-008 教训：不过滤会把离职者排第 1）
岗位画像组positions、岗位画像（JobProfileParsed：学历/年限/技能要求等）及 requirement_version四态判定的 required 要求值；版本号落库到 matching_records 支撑追溯
文件/知识库组files、知识库向量（Milvus）JD 原文来源、RAG 解释素材

三、我要输出给其他 Agent 的东西

① 给 Dify 组：两个工作流的输入 / 输出契约详见 18_Dify组对接需求文档.html

我 → Dify（我给它的输入）：

工作流输入变量内容
jd_parse 岗位画像解析jd_textJD 自然语言原文；要求只做语义提取不做判定，字段宁全勿缺
match_explain 匹配解释evidence_pack完整证据包 JSON：岗位 × 人才 × 四态判定 × 四维分 × 结构化证据清单（evidence_id / claim / source_table / source_value）

Dify → 我（我要它输出的，也是"我给其他 agent 输出啥"的反向答案）：

  • jd_parse：JobProfileParsed 结构化 JSON（纯 JSON、无 Markdown 围栏）
  • match_explain：MatchExplanation JSON —— summary / highlights / gaps / risks / interview_suggestions / pending_verification；每条结论的 evidence_ids 必须逐字存在于入参 evidences，否则五层校验剔除并记入 rejected_claims

我对 Dify 输出的处理：白名单过滤 + 五层证据校验 → 校验通过落库到 matching_records.explanation；Dify 失败 → llm_fallback（本地 Ollama）→ rule_fallback（规则），source 字段如实标注降级链。

② 给前端 / 编排对话 Agent：HTTP API（/matchings 前缀）这是我的"正式输出产品"

接口方法输出给对方什么
/matchings/runPOSTMatchRunResponse：batch_id + stats（候选/淘汰/待补全/输出数）+ 候选人列表（talent_id、rank、decision 四态、score、dimension_scores、matched_skills、hard_results、explanation_source）
/matchings/reversePOST双向匹配结果：人才适合的开放岗位排序 + 淘汰岗位逐条原因（只读不落库）
/matchings/explainPOSTMatchExplanation（含证据校验与 rejected_claims），被硬条件淘汰者也可调用（回答"为什么没出现"）
/matchings/batches/{batch_id}GET按批次回放完整快照（含零结果）
/matchings/positions/{id}GET岗位最新匹配结果（从库还原，不重算）
/matchings/talents/{id}GET该人才在各岗位的历史匹配记录
/matchingsGET匹配记录分页，支持 position_id / talent_id / min_score 过滤
/matchings/warnings/scanPOST触发预警扫描，返回闭环计数
/matchings/warnings + /{id}/resolveGET/POST预警分页查询 / 人工解决预警

编排层要点：把 explanation.source（dify / llm_fallback / rule_fallback）透传给对话用户，别把降级结果伪装成 Dify 产出；所有接口统一 SuccessResponse 包裹 + MATCHING_READ / MATCHING_RUN 权限。

③ 给储备预警 / 看板侧：派生数据基于落库数据二次加工

  • matching_batches + matching_records → 岗位储备健康度（零产出、PASS 人数、空缺天数）
  • reserve_warnings → 预警看板（分页、按类型/岗位/解决状态过滤）

四、一图记牢数据流

上游入库（别人写）：简历解析 → talents/resumes　岗位组 → positions/画像(version)　文件组 → files/Milvus ↓ 我只读 我跑批：召回(vector→sql_fallback) → 四态判定 → 四维打分 → 证据构建(726行) → Dify解释(校验/降级) ↓ 我写入（我入库的全部） MySQL：matching_batches(快照) + matching_records(明细+追溯5字段) + reserve_warnings(预警) Milvus：岗位画像向量(召回用) ↓ 我输出（我给别人的） Dify组：jd_text / evidence_pack（要回 JSON） 前端/编排Agent：/matchings/* 全套 API（batch_id 可回放，source 如实标注）
