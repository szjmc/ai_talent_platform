20 · 与人才数据决策 Agent 的交集与输出清单

岗位人才匹配 Agent 视角 · 基于真实代码核验（app/ai/agents/talent_agent.py、app/models/talent.py、app/services/evidence_builder.py、docs/CODEX_HANDOVER.md §5.7）· 2026-11-05

先说现状：代码层面的真话

"人才数据决策 Agent" = app/ai/agents/talent_agent.py（人才分析 Agent：读人才档案 + 简历 + 测评 + 培训记录 → LLM 生成画像 → 写 talent_portraits 表）。目前它是 32 行 TODO 骨架，无任何实现；交接文档 CODEX_HANDOVER §5.7 原文：「与人才决策 Agent（talent）的接口：无，匹配不依赖它的输出」。

所以：现在没有正在运行的接口，但表结构已经把交集点设计好了——趁对方还没动手，先把契约谈死。

一、四个真实交集点（表和字段已存在，可逐条核对）

#交集点方向代码依据
1 talents.potential_level（A/B/C/D 潜力等级） 我 ← 他 我的 quality 维打分直接读它：evidence_builder.py:53、matching_skill.py:135（POTENTIAL_SCORES 映射）。现状由 seed 脚本写演示数据；他实现后若画像里产生 potential_level，是否回写 talents 主表必须对齐，否则我的 quality 维永远是假数据
2 talent_portraits.suggested_positions（建议岗位） 我 → 他 他的画像字段之一是"建议岗位"（talent.py:174）。"建议岗位"如果没有真实匹配数据支撑就是编造——正确做法是调我的匹配接口拿事实，再写进画像
3 talent_portraits.dimensions（skill/experience/quality/potential 维度分） 互相校准 他的维度分是 LLM 生成的；我的 dimension_scores 是规则代码算的。两边口径不一致时，决策会自相矛盾，需要对齐"以谁为准"
4 AI 产物不得当事实证据 双向铁律 我的证据构建器明确排除 portrait_summary（AI 生成）作事实证据；talent_portraits 整表也是"AI 可重建数据"——他也同样不能拿我的解释文本（highlights/gaps）当事实，只能拿 matched_skills / hard_results / decision

二、我要输出给他什么（推荐契约）

① 首选：HTTP API（禁止让他直查我的表）

接口他传什么拿到什么用途
POST /matchings/reverse {"talent_id": x, "top_k": n, "weights": {...可选}} 该人才适合的开放岗位排序（score + decision 四态）+ 淘汰岗位逐条原因 生成画像的 suggested_positions 的事实依据；只读不落库
GET /matchings/talents/{talent_id}?limit=50 talent_id（limit 1-200） 该人才在各岗位的历史匹配记录（MatchHistoryItem 列表） 画像"建议岗位"引用历史结论；追踪人才流转
GET /matchings?talent_id=x&min_score=s talent_id / min_score 过滤 匹配记录分页 批量分析某人才被推荐情况
POST /matchings/explain position_id + talent_id 证据化解释（含 rejected_claims、pending_verification） 画像里"优势/短板"想引用某岗位结论时的复核入口

权限口径：他只需 MATCHING_READ（reverse/explain 会跑完整打分链路但属只读查询，批量高频调用需另行限流约定）。

② 字段语义约定（给他的"读数说明书"，最重要的一节）

类别字段他可以怎么用
事实（可作决策依据） decision（四态）、score、dimension_scores、matched_skills、hard_results、data_completeness 直接写进画像 / 用于决策；这些是规则代码产出 + 五层校验过的事实
解释（仅供参考） highlights / gaps / suggestion，并看 explanation_source 只能做参考文案。explanation_source=dify 是 LLM 产物；llm_fallback（本地 Ollama）/ rule_fallback 是降级产物，质量递减，画像引用时应降级措辞
警示信号（必须透传） pending_verification（待补全项）、recall_mode=sql_fallback（向量召回降级）、defaulted_dimensions（按默认值兜底的维度） 出现这些标记说明数据不全或走了降级，决策置信度要打折，不能当正常结果展示

对称铁律（交集点 4）：他给我回写画像时，我同样只把 talents.potential_level（若对齐回写）当事实证据；talent_portraits 里的 LLM 维度分/标签我不引入 hard_results 与证据包——防止"AI 解释引用 AI 解释"的循环污染。

三、我要反向跟他要的东西（谈判筹码，别只给不拿）

  • potential_level 回写对齐：talent_portraits 生成 potential_level 后，是否回写 talents.potential_level？回写则我的 quality 维有真实来源；不回写则该维应声明为演示数据（测评 Agent 侧同样有此待确认项）。
  • talents.status 维护责任：在职/离职/储备状态是我的召回过滤关键（MATCH-008 教训：离职者曾以 97 分排第 1）。要确认状态由简历组、决策侧还是 HR 人工维护，并要求变更可及时生效。
  • 画像版本通知：talent_portraits 是版本化的（version 每次重算 +1）。若他更新画像后希望我重新匹配，需要一个通知/触发约定（当前无任务队列，P1 缺口）。

四、一图记牢数据流

他（人才决策Agent，未实现）：talent_id → 读 talents/resumes/测评/培训 → LLM → talent_portraits(版本化) ↑ 我输出给他（API，MATCHING_READ） │ POST /matchings/reverse ← suggested_positions 的事实依据 │ GET /matchings/talents/{id} ← 历史匹配记录 │ POST /matchings/explain ← 结论复核（rejected_claims 一并给他） │ 读数规则：decision/score/matched_skills=事实；highlights/gaps=参考(看source)； │ pending_verification/sql_fallback/defaulted_dimensions=降级警示 ↓ 我反向要他（对齐后才有） │ talents.potential_level 回写（quality 维真实来源） │ talents.status 维护责任（离职过滤）
