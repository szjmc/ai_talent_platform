云端数据库 29 张表说明（大白话版）

库：ai_talent_platform @ 121.43.198.251（MySQL 8.0.27，共享库） · 整理日期：2026-11-05 · 全部表结构经真实连接核验

先记住一句话：这个库是全平台共用的，29 张表分属不同小组。你的岗位人才匹配 Agent 只写 3 张表（matching_batches、matching_records、reserve_warnings）+ Milvus 向量库，其余表要么只读、要么完全不用。

一、我的模块（岗位人才匹配 Agent）——核心中的核心

表名与我关系大白话说明存什么
matching_batches
跑批快照表		 我写入 ✔ 每次正式跑一次"岗位找人"，在这里记一本总账：哪天跑的、给哪个岗位跑的、当时的完整结果。哪怕一个人都没匹配上也要记一行——表示"我认真跑过这次"，不造假。 batch_id（批次号）、position_id、matched_at（时间）、response（完整结果 JSON）、request_scope（当时的筛选条件和权重，供以后"重放"复盘）
matching_records
人岗明细表		 我写入 ✔ 总账里的每一笔明细：某个岗位这次跑批，每个候选人得了多少分、为什么。一个候选人一行。这是 HR 最终看的数据。 score（0-100 总分）、dimension_scores（技能/经验/学历/素质四个分项）、highlights/gaps/suggestion（亮点/差距/建议）、hard_results（硬性条件四态判定）、explanation（AI 解释）、requirement_version（用的哪版岗位画像）、recall_mode（召回方式：vector 或 sql_fallback）、stats（统计计数）
reserve_warnings
储备预警表		 我写入 ✔ 报警记录本：扫描发现某岗位"招不到人/储备不够/空缺太久"就记一条，HR 处理完标记关闭。同一个岗位同类问题只留一条未处理的，不刷屏。 warning_type（三类：零产出/储备不足/长期空缺）、risk_level（high/medium）、message/detail（人话描述和数字）、resolved/resolved_at/resolved_by（处理留痕）

二、我"只读"的表——数据是别人家的，我借来用

表名与我关系大白话说明我用它的哪些字段
talents
人才档案表（52 人）		 我读取 ✔ 全公司的人才花名册：每个人一份档案。简历解析组负责往里写人，我负责从这里"挑人"。 skills / skill_tags（技能，评分和匹配的核心）、education + school + major（学历三件套，硬性判定用）、work_years（工作年限，硬性判定）、current_position、status（在职状态——离职的人绝不能被推荐出来，MATCH-008 的教训）、potential_level（A/B/C/D 潜力评级，我"素质分"的依据，目前是人才决策组该提供的）
positions
岗位表（0 行）		 我读取 ✔ 招聘岗位的登记簿。岗位组负责录入。⚠️ 目前是空的——这是我跑批的最大阻塞点，没有岗位就没法"岗位找人"。 岗位名、部门、城市、状态（开放/关闭）、关联的画像
position_requirements
岗位能力模型表（0 行，多版本）		 我读取 ✔ 岗位的"招聘标准说明书"：这个岗位要什么技能、几年经验、什么学历，技能各占多少权重。改一次标准就存一个新版本，我打分时认版本号，保证"当时按哪版标准打的分"说得清。 必备/加分技能清单、min_education、min_work_years、专业要求、技能权重、version（我落库时记进 matching_records.requirement_version）
resumes
简历表（1 行）		 间接读 简历原文和解析结果的家。人才是从简历"长"出来的，简历是源头。我一般不直接查它，但要解释"这个人技能哪来的"时可以追溯到简历。 简历文件地址、解析状态、解析后的结构化内容
resume_experiences
简历工作经历表（0 行）		 暂不用 简历里拆出来的"工作经历明细"：在哪家公司、干过什么、多久。给证据链做底料的，等简历解析组把它填上，我的证据会更扎实。 公司、职位、起止时间、职责描述
talent_portraits
人才画像表（4 行，版本化）		 谨慎对待 ⚠ 人才决策组用 AI 生成的人才画像（优势/短板/建议岗位）。铁律：AI 生成的画像不能进我的证据包——防止"AI 引用 AI"循环污染，我的证据只认数据库事实。潜在_level 是否回写 talents 表需要和对方对齐。 dimensions（四维画像，现在 4 条全是空的 { }）、strengths/weaknesses、suggested_positions、potential_level

七、我模块的信息存储地图（一张图记住）

跑批一次，数据流是这样的：

① 读：talents（挑人+技能/学历/状态）+ positions + position_requirements（岗位标准和权重）
② 召回：优先 Milvus 向量召回（recall_mode=vector）；Milvus 挂了自动降级 SQL 召回（如实记 sql_fallback）
③ 写 MySQL：matching_batches 记 1 行总账 → matching_records 每个候选人 1 行明细（含四态判定、四维分、AI 解释、5 个追溯字段）
④ 预警扫描：reserve_warnings 记录零产出/储备不足/长期空缺三类警报

Milvus 向量库里我存什么：岗位画像文本的向量（bge-m3 模型，1024 维），用于"语义找相似人才"。不存人才向量（那是简历组的活）。

明确不落库的（只读试算）：POST /matchings/reverse（人才找岗位）和 POST /matchings/explain（解释）——代码注释写明不写表，别让别的组误以为有留痕。
当前数据现状速览（2026-11-05）：talents 52 人数据质量好（零缺失、技能 JSON 规整）；positions 和 position_requirements 0 行——你跑批前必须先有岗位数据（催岗位组，或自插 [test] 测试岗位）；matching 三表全 0 等待首跑；1 条脏数据：某人才 education 字段填了字面量 "string"；talent_portraits 4 条 dimensions 全空，需反馈人才决策组。

八、给你的三条使用纪律（共享库）

1. 只写自己的三张表——其他 26 张表谁的都不碰，尤其别 drop 别人的表；talents/positions 那是人家组的资产。

2. 测试数据带标识——matching_records 全组可见，测试岗位名带 "[test]" 前缀、测完可清理；别在库里放敏感或编造的内容。

3. 每次结构变更留 SQL 迁移脚本——你的 matching 三张表就是靠 docs/sql/ 下三个脚本在云端建出来的，以后加字段也照这个规矩，脚本进 git、云端执行、验证留痕。
