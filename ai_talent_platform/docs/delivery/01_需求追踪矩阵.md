## 三、与任务书第二阶段的逐条核对（业务红线）

| 红线要求 | 是否满足 | 证据 |
| --- | --- | --- |
| 仅 FAIL 可淘汰 | ✅ | `judge_hard_conditions` 只把 FAIL 交给 `excluded`；UNKNOWN/NEEDS_REVIEW 一律保留（实测王强保留） |
| UNKNOWN 不得默认 PASS | ✅ | UNKNOWN 按 15% 降权参与打分，且写入 `defaulted_dimensions`，`stats.unknown` 单独计数 |
| NEEDS_REVIEW 转人工 | ✅ | 结果中保留该候选人并标记，解释里给出「需人工复核」项；不进入淘汰 |
| 必备 / 优先分离 | ✅ | `required_skills` 参与硬判定，`preferred_skills` 只加分；同一技能同时出现以「优先」为准 |
| 分数 0~100 且代表相对适配度 | ✅ | Schema `ge=0, le=100`；实测 99.5 / 98.0 / 24.22，非百分制原始分 |
| 证据须真实字段或确定性计算 | ✅ | `evidence_builder` 只读档案字段与判定结果；`missing` 证据不带能力术语 |
| missing 不能证明能力 | ✅ | 单测 `test_missing_evidence_cannot_prove_capability`；`capacity_terms=[]` |
| Evidence ID 唯一可追溯 | ✅（有遗留） | `EVID-{pid}-{tid}-{seq}`；跨批次唯一性待复合键（F-3） |
| ExplanationClaim 必须引用有效 evidence_ids | ✅ | 无 `evidence_ids` 的结论直接丢弃并记入 `pending_verification` |
| Dify 只做自然语言，不决定硬条件/评分/排序 | ✅ | 硬条件与打分全在 Python；Dify 仅在 `explain` 节点、且输出必经校验 |
| Dify/LangGraph 不得绕过 Service 访问 DB | ✅ | 工作流只调 pipeline 方法；`matching_workflow.py` 内无 SQL、无 session |

## 四、结论

- **业务主链路（解析 → 确认 → 召回 → 判定 → 打分 → 证据 → 解释 → 校验 → 落库 → 回读）已真实跑通**，有真实进程 + 真实库 + 真实 HTTP 的完整证据。
- **4 个 PARTIAL 全部是「外部依赖未接通」或「已知结构缺口」**，不是「没写」：Dify 密钥/契约、Milvus、LLM 密钥、批次表 DDL。
- **没有任何一项被降级实现**（没有为了通过测试改业务规则，没有用 Mock 顶替真实功能）；未接通的通道一律在响应字段与日志中如实标注。
