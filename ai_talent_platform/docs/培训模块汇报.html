01模块定位与边界

一句话：消费测评的差距，产出可执行的学习计划，并把结果送回测评。 上游不产出数据，下游不改别人的表——这是本模块最需要说清楚的一件事。

只读别人的表（不写）

  • talents 校验人才存在、读 current_position
  • positions 岗位标题匹配
  • position_requirements 能力模型定标准
  • assessments / assessment_results gaps 兜底

自己的表（全权）

  • courses 课程库
  • training_plans 计划主体
  • plan_courses 计划-课程关联
  • learning_records 学习与考核记录
边界声明（答辩常问）：不做测评出题与打分、不做人才建档与简历解析、 不做岗位能力模型维护、不做前端页面与推送渠道、不做课程内容生产、 不做培训 A/B 实验（单企业样本量不足，统计上不成立）。

02整体业务流程全景

六个节点串成一条主链路，其中节点 5 是独立的定时任务而不是流程里的一步， 节点 6 通过事件回流测评形成闭环。这是本模块在架构上最关键的两个判断。

主链路　POST /trainings/plans/generate　→　节点 1~4 一次完成（秒级）
支线　/records · /progress · /lag-scan · /score　→　跨越 4 周持续发生（按需 / 定时）

节点契约一览

节点干什么 输入 → 输出代码位置
1短板诊断 gaps[] → 带 delta / priority / est_hours 的短板列表 diagnose_gaps
2方案排期 短板列表 + 周数/学时约束 → 周次 × 维度 × 学时的骨架 rule_schedule
3课程匹配 骨架 + 课程库 → 带 course_id 的完整课表 match_courses
4推送存档 课表 → training_plans + plan_courses + 事件 create_plan
5进度跟踪 时间进度 vs 完成学时 → 正常 / 提醒 / HR 预警 compute_progress
6考核复测 分数 + 及格线 → 通过则发复测事件，未过发调整事件 assess

03六个节点逐一详解

每个节点写清四件事：拿什么、算什么、守什么约束、怎么验证。 所有阈值集中在 training_logic.py 顶部， 改一个数就能做对照实验。

1

短板诊断 —— 决定「学什么」

规则引擎 · 模型不参与
输入测评给的 gaps[]，或 position_id + 只带 current 的分数；岗位能力模型自动补 required 与 weight
输出过滤排序后的短板列表，每项带 delta、priority、est_hours
delta = required − current　　缺口 ≤ 0 直接剔除，不排课
delta ≥ 20 → P0　｜　delta ≥ 8 → P1　｜　其余 → P2
权重 ≥ 0.25 的岗位关键维度　→　直接抬到 P0
est_hours = clamp(round(delta / 4) + 2, 3, 8)

为什么这么设计

  • 已达标不排课：缺口 ≤ 0 剔除，避免"考了 85 分还让学 80 分要求的内容"
  • 权重能越级：缺口只差 5 分但权重 0.3 的维度，直接 P0——岗位最看重的能力，哪怕差一点也要优先补
  • 标准可溯源：响应带 requirement_source（position_model / explicit / default），用了谁的标准一目了然
实测证据：同一份分数、换岗位标准，排序结果不同——数据分析师把「SQL 与数据库」排第一， AI 产品经理把「需求分析」排第一（后者权重 0.25 命中关键维度阈值）。这就是「千人千面」的实际来源。
2

方案排期 —— 决定「怎么排」

LLM 编排 · 规则守底线
输入短板列表 + 周期约束（默认 4 周 / 每周 8 学时）
输出week × dimension × hours 的排期骨架，同周同维度合并
总量 = Σ est_hours　｜　容量 = max_weeks × max_hours_per_week
总量 > 容量　→　抛 CapacityExceeded，提示「建议延长至 N 周」
单个学习单元最长 4 学时，避免一门课压满整周

LLM 在这里做什么、不做什么

会做

  • 决定每个短板分到第几周
  • 为每周写一句人话理由
  • 在约束内做更自然的分布

拿不到

  • 课程库（结构上不给）
  • 约束校验权（legal_skeleton 拦截）
  • 自由发挥空间（维度必须在短板内）
关键：模型只拿到「短板 + 约束」，拿不到课程池。 这是刻意从信息结构上断掉它编造课程的可能——不是靠提示词求它别乱写。
3

课程匹配 —— 决定「用什么教材」

SQL + 规则 · 模型不参与
输入排期骨架 + courses 表 + 该学员已学过的课程 ID
输出每项挂上 course_id / title / level，或降级为外部学习建议
匹配条件：category 相同 或 skill_tags 命中
排除：已学过（learned）、本计划已占用（taken）
层级贴合：目标层级 ±1 档内；无贴合则取最接近的一门
同层多门时：学时长的优先

缺课怎么办

库里找不到对应课程时，不编造课程名：该项标记 is_platform=false、 title=null，另给一条 external_suggestion 外部学习方向建议， 并计入 external_count。

实测证据：正常链路 library_rate = 1.0（课程 100% 来自课程库）； 清空课程库后 external_count > 0、title = null，且不报错。
4

推送存档 —— 落地 + 写说明

LLM 写文案 · 事实已固定
输入完整课表 + 学员姓名 + 统计量（周数、总学时、降级项数）
输出training_plans 主记录 + plan_courses 明细 + training.plan_created 事件 + 80–120 字方案说明

这一步模型只做一件事：把已经算好的数字讲成人话。 排期、总量、课程、及格线全部是既定事实，模型改不动。

created_by_ai = (generated_by == "llm")　→　前端显示「AI 生成」标识
summary_source = "llm" | "rule"　→　说明文案的来源，可追溯
容错：事件发布失败不影响主流程（计划已落库就算成功）， 避免通知模块抖动导致培训计划创建失败。
5

进度跟踪 —— 决定「谁掉队了」

独立定时任务 · 规则
输入计划总学时、时间流逝比例、已完成学时
输出预期学时、落后比例、完成率、四级判定 + 对应事件
expected = total × elapsed
lag = (expected − done) / total
落后 ≥ 40% → HR 预警（training.lag.alert）
落后 ≥ 20% → 提醒（training.lag.remind）
完成 ≥ 总量 → 已按期完成

为什么不做成流程里的循环

进度跟踪跨越 4 周、持续发生，与"生成计划"不是同一个时间尺度。 做成流程节点会导致长事务挂起、无法单独重跑。 因此拆成 POST /trainings/lag-scan 独立入口，由调度器定时调用， 可重入、可单测、可手工补扫。

6

考核复测 —— 闭环回测评

规则 + 事件
输入考核分数、及格线（默认 80）、是否允许自动复测
输出判定结果 + training.retest.required（通过）或 training.plan.adjust（未过）
score ≥ 80　→　通过，发复测事件，回流上游测评安排重考
score < 80　→　发调整事件，HR 人工介入修改计划
auto_retest = false　→　只记录，不发事件（HR 可关）
闭环意义：培训不是终点。达标 → 触发复测 → 测评重新出分 → 若仍有差距则再生成计划。这条事件就是与上游测评模块的唯一耦合点，双方不用互相调用。

五层单向依赖：路由 → 服务 → 智能/规则双轨 → 仓储 → 数据库。 核心设计是「业务算法下沉到零依赖的纯函数层」，因此规则引擎可以完全脱离数据库单测。

分层为什么要这样切

SQL 只有一个出口

所有查询集中在 training_repository.py 的 6 个 Reader。 换库、加缓存、加审计都只需改这一处。

模型只有一个出口

只有 training_agent.py 碰 LLM。 换模型、加开关、做降级，影响面被锁在一个文件里。

05智能在哪里 —— 双轨设计

这是评审最容易追问的一点：「你这个模块到底有没有智能？还是把阈值写死了？」 答案要诚实：六个节点里，两个用到模型，四个是确定性算法—— 这是经过权衡的选择，不是能力不足。

节点谁做决策 模型参与方式可复算
1规则引擎 不参与。保证可解释、可复算、可测试是
2LLM 编排 + 规则守底线 只拿短板与约束，输出周次/维度/学时 + 每周理由；不碰课程部分
3SQL + 规则 不参与。课程必须是库里真实存在的实体是
4LLM 写说明 基于已确定的事实，写 80–120 字方案说明部分
5规则 不参与是
6规则 + 事件 不参与是

为什么不全交给模型

培训排期是强约束优化问题：学时不能超上限、周数不能超、课程必须真实存在、 学过的不能重排。让模型自由生成，编造课程几乎是必然事件—— 它会写出「《高级需求分析实战》8 学时」，而这本书根本不存在。

所以采用「模型编排 + 规则守底线」：模型负责它擅长的（排期理由、方案解释、 自然语言表达），规则负责它擅长的（约束校验、实体挂载、可复算）。 这也是 library_rate 能稳定为 1.0 的原因—— 不是模型乖巧，是它从结构上拿不到编造的机会。

防幻觉的三道结构性闸门

闸门 1 · 信息隔离

排期节点的 prompt 里不含课程库。模型想编课程，得先知道有哪些课，而它看不到。

闸门 2 · 结构校验

legal_skeleton() 逐项校验：维度必须在短板内、周次在范围内、学时为正且不超上限。 不合法直接回退，不做"尽量修补"。

闸门 3 · 实体强绑定

课程只能由 match_courses() 从数据库里选出来， 模型输出里根本没有课程字段可填。

回退阶梯 —— 任何一步失败都不中断主流程

层级触发条件行为标记
1未配 API Key不发请求，直接规则排期（避免 5–8 秒重试与一屏 401） generated_by=rule
2模型超时 / 报错回退规则排期，记录 warning 日志 generated_by=rule
3输出结构不合法legal_skeleton 拦截后回退 generated_by=rule
4说明文案失败或过短回退模板文案 summary_source=rule
零 Key 也能跑通六节点全流程——这是刻意保留的能力，用于离网演示与答辩兜底。 实测：清空 LLM_API_KEY 后重新生成，返回 generated_by=rule， 流程不中断、不报错、不卡顿。

模型接入方式

内置的 qwen / openai 适配器把官方地址写死在类属性里， 只改 .env 的 LLM_BASE_URL 对它们完全无效。 TrainingAgent._use_custom_endpoint() 会检测「配置地址 ≠ 内置地址」， 自动改用模块内自建的 OpenAI 兼容客户端，不需要修改公共层任何文件。

# .env（已被 .gitignore 忽略，不会进仓库）
LLM_MODEL=deepseek-chat
LLM_API_KEY=sk-****
LLM_BASE_URL=https://api.deepseek.com/v1

切回通义：把三行改回 qwen-plus / DashScope 的 key 与地址即可，代码不用动。 这就是选择「OpenAI 兼容协议」而不是绑定单一厂商的价值。

06数据模型与流转

四张自有表 + 三组只读表。数据流向是单向的：标准 → 计划 → 明细 → 过程记录， 每一层都能反查到上一层，不存在环形依赖。

表行数 作用写入方
position_requirements3 岗位能力模型：各维度要求分 + 权重，权重强制合计 1.0 seed 脚本（HR / 岗位模块维护）
courses19 课程库，8 个能力维度，L1–L4 分级 seed 脚本 / 管理接口
training_plans4 计划主体，含 created_by_ai 标识 /plans/generate
plan_courses13 计划-课程关联，含学习顺序与是否必须通过 计划创建时批量写
learning_records39 学习进度与考核成绩，通过率的分母来源 /records、/score
设计要点：learning_records.plan_id 允许为空，表示「先有学习行为、后归入计划」。 因此统计通过率时不能用 plan_id 做内连接，否则这批数据会被静默漏掉。 这个坑在自检里加了断言。

一个容易被忽略的表设计

learning_records 上有 suspicious 字段——刷课标记。 判定规则：进度 100% 但学习时长少于阈值 → 标记可疑，不计入有效统计。 这是培训场景里很实际的需求（挂机刷学时），也让数据可信度有了兜底。

7.2 上游契约：gaps 结构

推荐写法（只给分数）

{
  "talent_id": 2,
  "position_id": 1,
  "gaps": [
    {"dimension": "需求分析", "current": 62},
    {"dimension": "数据分析", "current": 55}
  ]
}

目标分和权重由岗位模型补。测评侧只管「考了多少分」，标准归岗位模块维护， 两边职责不混。

完整写法（自带标准）

{"dimension": "需求分析",
 "current": 62,
 "required": 85,
 "weight": 0.30}

required / weight 可不传，不传则依次取 岗位模型 → 默认值（80 分 / 0.2 权重）。delta 由本模块计算。

最隐蔽的坑：维度名必须与 courses.category 一字不差。 多两个字不会报错，只会让该维度静默降级为「无课可推」。 已在自检里加了交叉校验，避免这类沉默失败。

7.3 下游契约：四个事件

事件时机载荷要点
training.plan_created方案落库后 plan_id / talent_id / total_hours / channels
training.lag.alert落后 ≥ 40% plan_id / talent_id / lag_ratio / level
training.lag.remind落后 ≥ 20% 同上，级别为提醒
training.retest.required考核通过 plan_id / talent_id / dimensions / assessment
training.plan.adjust考核未通过 plan_id / talent_id / score

现状说明：本模块只负责发布事件。接住它们需要公共层注册订阅者， 而当前全项目还没有任何 subscribe 调用——这是全项目级的待办，不由本模块决定。 在订阅者补齐之前，「测评 → 培训」的自动触发需要外部显式调用 /plans/generate。

08质量保障

四层测试，一条命令跑完，约 34 秒。设计原则是能测纯函数就绝不测接口—— 算法层零依赖，因此最快的测试只要 0.3 秒。

层测什么 数量耗时 覆盖点
L1纯算法单元 210.3s 诊断 / 排期 / 匹配 / 进度 / 考核五组边界条件，无数据库
L2真库集成 23~8s 走真实 MySQL，含岗位模型与通过率共 9 条；库不可用则自动 skip
L3全项目回归 71~20s 架构分层、ORM 映射、公共层契约，确认没碰坏别人
L4接口探针 4~5s ASGI 直连不占端口，验路由注册与鉴权生效

本模块自有测试 44 条（L1 21 + L2 23），L3 为全项目公共回归。 运行方式：python scripts/selfcheck.py 或双击 一键自检.bat。

09六个设计决策

这部分回答「为什么这么做」。每一条都对应一个可被追问的取舍。

决策理由
算法层零依赖 业务算法不 import sqlalchemy / pydantic / fastapi，因此能脱离框架秒级单测。 代价是要多写一层数据传参，收益是 21 条测试 0.3 秒跑完、改阈值敢改。
模型拿不到课程库 防幻觉不能靠提示词。把课程从模型可见信息里删掉，它就没法编造。 这是结构约束，不是道德约束。
进度跟踪独立成任务 跨越 4 周的事不该挂在一次请求里。拆成独立入口后， 调度器可重试、可补扫、可单独测试。
闭环靠事件不靠调用 培训要通知测评复测，但直接调测评服务会造成双向依赖。 改成发事件，双方只依赖事件名。
降级必须可见 课不够、标准缺失、模型挂掉——一律在响应里标记（library_rate / requirement_source / generated_by）， 绝不静默用默认值假装成功。
AI 能力可开关 按 use_ai 参数与 Key 是否配置双重判断。 离线演示、成本控制、故障降级三种场景用同一套代码。

10已知不足与演进路线

主动说明短板，比被问出来更好。以下四项都已在代码或文档中留下明确标记，不是隐性风险。

不足影响计划优先级
课程库仅 19 门 需求要求 60–80 门。当前每个能力维度平均只摊到 3 门， 导致匹配结果重复度高、可选空间小 按 8 个维度 × 每维度 8 门扩充，保持 L1–L4 梯度完整 高
成长轨迹趋势接口未做 需求 102 要求展示能力变化曲线，当前只有单次计划视角 基于 learning_records + 测评历史做时间序列聚合 高
事件无订阅者 四个事件已发布但全项目无 subscribe， 闭环需外部显式调用触发 公共层注册订阅者（跨模块，需协调） 中
无 AI 出题 / 批改 考核目前只录分数，题库与自动评分未实现 基于课程知识点让模型出题，需人工审核环节 中
关于 Dify 等模型中台的选型结论：培训模块当前不依赖。 本模块只有两处单轮文本生成（排期骨架、方案说明），用不上工作流编排、 知识库 RAG、Prompt 后台可视化配置——这些是中台的核心价值，不是本模块的诉求。

需要说明的是：Dify 在本项目里由 Dify 组在其它模块接入（适配器与路由在 develop 上已实现）， 与本模块是并行能力而非替代关系。本模块只依赖「OpenAI 兼容协议」这一层抽象， 换直连或换中台都不用改业务代码。

真正该补的是数据（课程库 19 → 60~80 门）和功能（成长趋势、AI 出题）， 这两件事上不上中台都得做。

11答辩预案

十个最可能被问到的问题，按「先给结论、再给依据」组织。

Q1这个模块到底哪里"智能"？阈值不是写死的吗？
六个节点里两个用模型：排期编排和方案说明。 四个用规则是刻意的——培训排期是强约束优化，模型自由生成必然编造课程。 我的选择是「模型做它擅长的表达与编排，规则守约束底线」。 智能体现在因岗而异的标准合并与约束内的自然排期， 不是体现在"让模型什么都干"。
Q2凭什么说课程不是模型编的？
三重结构性保证：① 排期的 prompt 里不含课程库，模型看不到有哪些课； ② 模型输出的结构里没有课程字段，想填也没位置； ③ 课程只能由 match_courses() 从数据库选出。 所以 library_rate 稳定为 1.0 是结构决定的，不是模型表现好。
Q3模型挂了怎么办？演示现场没网怎么办？
四级回退：无 Key 不发请求 → 超时报错回退 → 结构不合法拦截回退 → 文案失败用模板。 全程 generated_by=rule 标记，流程不中断。 零 Key 也能跑通六节点，可以现在拔掉网线演示。
Q4为什么不做成端到端的 Agent，一次对话出结果？
因为要可审计。培训计划涉及学时、预算、考核标准， 出了问题必须能回答"这 22 学时是怎么算的"。 纯 Agent 给不出可复算的中间量。可解释性优先于自动化程度。
Q5"千人千面"具体差在哪？
同一份分数，换岗位标准结果就不同。数据分析师权重最高的是 「SQL 与数据库」0.30，AI 产品经理是「需求分析」0.25—— 权重 ≥ 0.25 会直接抬到 P0，所以两人拿到的课表顺序、重点完全不同。 可以现场跑 demo_training.py 看两段输出对比。
Q6课不够的时候会怎样？
不编造。该项标 is_platform=false、title=null， 另给外部学习方向建议，并计入 external_count 在响应里明示。 当前课程库只有 19 门，这个降级路径是会被实际触发的——我把它当特性测过。
Q7怎么证明没影响别人的模块？
17 个新文件全是本模块自有；5 个修改也都是本模块文件的能力扩充， 真正触及其他目录的只有 4 处追加式登记（挂路由、注册技能、加提示词）， 没有改动任何既有逻辑分支。 全项目 71 条回归测试通过，架构分层测试也在其中。
Q8事件发出去没人接，算完成了吗？
本模块的职责到"发布"为止，订阅者属于公共层，全项目目前都没有。 我不越界去改别人的模块，但在文档里明确标注了这个断点。 短期靠外部调用 /plans/generate 触发，长期由公共层补订阅。
Q9为什么培训模块不接 Dify？
因为本模块对模型的诉求只有两件事：排周次、写一段说明，都是单轮无状态生成。 编排、RAG、Prompt 后台这些中台能力一个都用不上。 Dify 由 Dify 组在其它模块接入，与本模块并行而非替代。 本模块只依赖 OpenAI 兼容协议，将来真要接中台也只是换一个客户端，业务代码不用动。 选型按需求，不按热度。
Q10代码提交了吗？怎么复现？
见下一节，六条命令从零到端到端演示。 测试一条命令跑完四层，约 34 秒出全部结论。

python scripts/demo_training.py
