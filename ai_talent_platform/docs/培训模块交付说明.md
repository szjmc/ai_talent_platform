# 智能培训赋能 Agent · 模块交付说明

> 对应需求文档 2.4 节，对应 `app/ai/agents/training_agent.py` 等 11 个文件。
> 本文档回答四件事：**是什么、怎么跑、验收怎么看、边界在哪。**

---

## 1. 一句话定位

**拿到测评给出的能力短板，排出 4 周课表，从课程库挂真实课程，推给员工，盯 4 周进度，考核达标后通知测评复测。**

上游是**智能测评 Agent**（给它 gaps），下游回到**测评**形成闭环。中间不做鉴权、不建人才档案、不写前端——那些是别人的模块。

| 环节 | 谁做 | 交接物 |
|---|---|---|
| 出能力分 | 测评 Agent | `gaps[]`（维度 / 当前分 / 要求分 / 权重） |
| 排培训方案 | **本模块** | `training_plans` + `plan_courses` |
| 学完复测 | 测评 Agent | 事件 `training.retest.required` |

---

## 2. 六个节点与代码位置

| 节点 | 干什么 | 代码 | 关键约束 |
|---|---|---|---|
| 1 短板诊断 | 剔已达标项、算优先级（P0/P1/P2）、估学时 | `training_logic.diagnose_gaps` | 缺口 ≤0 直接剔除，不排课 |
| 2 方案排期 | 4 周、每周 ≤8 学时、末周留考核 | `rule_schedule` / `legal_skeleton` | 装不下就报错，不偷塞学时 |
| 3 课程匹配 | 维度 → 课程库真实课程 | `match_courses` | **课程 100% 来自库，缺课降级不编造** |
| 4 推送存档 | 落库 + 推送记录 + `training.plan_created` | `TrainingService.create_plan` | 事件失败不影响主流程 |
| 5 进度跟踪 | 时间进度 vs 完成学时，判级发事件 | `compute_progress` / `scan_lag` | **独立定时任务，不写在图里循环** |
| 6 考核复测 | 结课评分，达标回流测评 | `assess` / `submit_score` | 复测走事件，HR 可关 |

纯算法集中在 `app/ai/agents/training_logic.py`（**零第三方依赖**，可脱离框架单测），业务编排在 `app/services/training_service.py`。

## 3. 启动（6 条命令）

```bash
# 1) 依赖
pip install -r requirements.txt

# 2) 环境：复制模板并填本机 MySQL 密码（.env 已被 .gitignore 忽略，不会进仓库）
cp .env.example .env

# 3) 建库建表（25 张表）
python scripts/init_db.py

# 4) 课程库（19 门 / 8 个维度）—— 不跑这步，节点 3 会全部静默降级

# 5) 岗位能力模型（3 个岗位）—— 不跑这步，节点 1 退回默认标准（不会报错，但千人千面失效）
python scripts/seed_position_requirements.py --bind

# 6) 端到端演示（六节点一次跑完，答辩可直接投屏）
python scripts/demo_training.py
```

起服务后看接口文档：`python main.py` → <http://127.0.0.1:8000/docs> → 培训管理。

**没配 LLM Key 也能跑**：节点 2 会自动走规则排期（`generated_by=rule`），全程不报错、不等重试。

## 5. 对外契约（给其他模块）

### 5.1 入参：`gaps`

```json
{"dimension": "需求分析", "current": 62, "required": 85, "weight": 0.30}
```

- `current` **必填**（没有当前分就算不出缺口，宁可报错也不静默丢弃）；
- `required` 与 `weight` **可以不传**——不传时依次取「岗位能力模型」→「默认值（80 分 / 0.2 权重）」。
  这样测评 Agent 只需要给出「考了多少分」，岗位标准由岗位模块维护，两边职责不混；
- `delta` 可不传，本模块按 `required - current` 计算；
- **维度名必须与 `courses.category` 一字不差**。多两个字不会报错，只会让该维度静默降级——这是本模块最隐蔽的坑，已在自检里加交叉校验。

### 5.2 出参：计划

`items[]` 含 `week / dimension / hours / course_id / title / level / is_platform / reason`；
顶层含 `library_rate`（课程来自库比例）、`external_count`（降级项数）、`assessment`（考核节点）、`summary`（可解释说明），
以及 `requirement_source / requirement_position_id / requirement_version`（本次用了谁的标准，见 5.4）。

### 5.3 事件（订阅方按需接）

| 事件 | 时机 | 载荷要点 |
|---|---|---|
| `training.plan_created` | 方案落库后 | `plan_id / talent_id / total_hours / channels` |
| `training.lag.alert` / `training.lag.remind` | 进度落后达阈值 | `plan_id / talent_id / lag_ratio / level` |
| `training.retest.required` | 考核通过 | `plan_id / talent_id / dimensions / assessment` |
| `training.plan.adjust` | 考核未通过，需人工调整 | `plan_id / talent_id / score` |

`training.retest.required` 就是**回流测评 Agent 的接口**：测评侧订阅它去安排复测，不需要本模块直接调用测评。

> 现状提醒：本模块只负责**发布**事件，接住它们需要公共层注册订阅者（当前全项目还没有 `subscribe`）。
> 在订阅者补齐之前，「测评 → 培训」的自动触发需要外部调用 `/plans/generate`。

### 5.4 岗位能力模型（标准从哪来）

节点 1 判断「什么叫短板」需要两个标准：目标分 `required` 和岗位权重 `weight`。
它们不属于测评结果，而是来自岗位模块的 `position_requirements` 表（`dimensions` + `weights`，JSON，多版本）。

**解析顺序（拿不到就明确降级，绝不编造）**：

1. 调用方显式传 `position_id` —— 最准，优先；
2. 人才表里的 `current_position` 文本 → 去 `positions.title` 精确匹配；
3. 都拿不到 → 回退默认值（80 分 / 0.2 权重）。

**响应里一定会告诉你用了哪个标准**：

| `requirement_source` | 含义 |
|---|---|
| `position_model` | 采用了岗位能力模型（附带 `requirement_position_id` 与 `requirement_version`） |
| `explicit` | 调用方传的 `gaps` 自带标准，尊重调用方口径 |
| `default` | 既没有岗位模型也没传标准，用的是默认值 |

**维护方式**：`python scripts/seed_position_requirements.py`（幂等，可重复跑；`--bind` 会把演示人才的现职位绑到岗位，`--list` 只查看）。
脚本会强制校验**权重合计 = 1.0**，避免「权重加不到 1 导致优先级失真」。

> 数据库里 `positions` / `position_requirements` 原本是空的，所以「岗位模型」这条链路必须先跑一次 seed 才能演示。
> 不跑也不会报错，只是退回默认标准——**降级是显式的，不会假装用上了岗位模型**。

## 6. AI 能力与回退策略

### 6.1 哪些环节真的用了模型

| 节点 | 谁在做决策 | 模型参与方式 |
|---|---|---|
| 1 短板诊断 | 规则引擎 | 不参与（保证可解释、可复算、可测试） |
| 2 方案排期 | **LLM 编排，规则守底线** | 只拿到短板与约束，**拿不到课程库**；输出周次/维度/学时 + 每周理由 |
| 3 课程匹配 | SQL + 规则 | 不参与（课程必须是库里真实存在的实体） |
| 4 推送存档 | **LLM 写说明** | 基于已确定的事实，写 80–120 字方案说明 |
| 5 进度跟踪 | 规则 | 不参与 |
| 6 考核复测 | 规则 + 事件 | 不参与 |

判定字段：计划响应里的 `generated_by`（`llm` / `rule`）与 `summary_source`（`llm` / `rule`），前端据此显示「AI 生成」标识。

### 6.2 为什么不全交给模型

培训排期是**强约束优化问题**：学时不能超上限、周数不能超、课程必须真实存在、学过的不能重排。让模型自由生成，编造课程几乎是必然。
所以采用「模型编排 + 规则守底线」：模型负责它擅长的（排期理由、方案解释），规则负责它擅长的（约束校验、实体挂载）。

这也是 `library_rate` 能稳定为 **1.0**（课程 100% 来自课程库）的原因——不是模型乖巧，是它从结构上拿不到编造的机会。

### 6.3 接第三方兼容端点（如 DeepSeek）

内置的 `qwen` / `openai` 适配器把官方地址写死在类属性里，只改 `.env` 的 `LLM_BASE_URL` 对它们无效。
`TrainingAgent._use_custom_endpoint()` 会检测「配置地址 ≠ 内置地址」，自动改用模块内自建的 OpenAI 兼容客户端，**不需要修改公共层任何文件**。

```bash
# .env（已被 .gitignore 忽略）
LLM_MODEL=deepseek-chat
LLM_API_KEY=sk-xxx
LLM_BASE_URL=https://api.deepseek.com/v1
```

切回通义：把上面三行改回 `qwen-plus` / DashScope 的 key 与地址即可，代码不用动。

### 6.4 回退阶梯（任何一步失败都不中断主流程）

1. **未配 Key** → 直接规则排期，不发请求（避免 5~8 秒重试与一屏 401）
2. **模型超时/报错** → 回退规则排期，`generated_by=rule`
3. **输出结构不合法** → `legal_skeleton` 校验拦截，回退规则排期
4. **说明文案失败或过短** → 回退模板文案，`summary_source=rule`

**零 Key 也能跑通六节点全流程**，这是刻意保留的能力（离网演示、答辩兜底）。

## 9. 验收自测清单

```bash
pytest tests/test_training_logic.py                  -q   # 21 条纯算法，零依赖
pytest tests/test_training_service.py                -q   # 23 条真库集成（MySQL 不可用时自动 skip）
pytest tests/test_training_position_and_passrate.py  -q   # 岗位模型 + 通过率（含在 23 条里）

python scripts/selfcheck.py     # 一键四层自检（L1 单元 / L2 集成 / L3 回归 / L4 接口）
```

| # | 验收项 | 怎么看 |
|---|---|---|
| 1 | 已达标维度不排课 | 张伟「沟通表达 82/80」不出现在计划里 |
| 2 | 课程 100% 来自课程库 | 返回 `library_rate == 1.0`，且每项都有 `course_id` |
| 3 | 缺课不编造 | 清空课程库再生成 → `external_count>0`、`title=null`、有 `external_suggestion` |
| 4 | 学时不满溢 | `total_hours ≤ max_weeks × max_hours_per_week` |
| 5 | 容量不足报错 | `max_hours_per_week=2` → 明确提示「建议延长至 N 周」 |
| 6 | 进度不可回退 | 提交更小 progress → `ParamError` |
| 7 | 刷课可识别 | 100% 进度只学 1 分钟 → `suspicious=true` |
| 8 | 滞后发事件 | 落后 ≥50% → `training.lag.alert` |
| 9 | 达标回流复测 | 88 分 → `training.retest.required`；`auto_retest=false` 不发 |
| 10 | 全达标不报错 | 五项全过 → 返回「无需培训」，不是异常 |
| 11 | **岗位模型生效** | 只传 `current` + `position_id=1` → `requirement_source=position_model`，目标分取自岗位表 |
| 12 | **同一份分数换岗位结果不同** | `python scripts/demo_training.py` 的「节点 1 补充」段，两个岗位的短板排序不同 |
| 13 | **无岗位模型时明确降级** | 岗位没维护模型 → `requirement_source=default`，目标分 80，不报错也不假装 |
| 14 | **通过率可统计** | `GET /trainings/stats/pass-rate` → 返回整体与按课程拆分，未考核的不进分母 |
| 15 | **整计划考核能落库** | 不传 `course_id` 提交 88 分后，该计划下每门课都有考核记录（否则通过率恒为 0） |
| 16 | **AI 排期真的生效** | `use_ai=true` → `generated_by=llm`、`model_name` 非空，且每项 `reason` 是模型写的人话而非模板 |
| 17 | **AI 方案说明可用** | `summary_source=llm`；说明里出现的课程名必须都能在 `courses` 表查到 |
| 18 | **模型不可用静默回退** | 清空 `LLM_API_KEY` 再生成 → `generated_by=rule`，流程不中断、不报错 |

## 10. 边界（明确不做什么）

- **不做**测评出题与打分（读测评结果，不写）；
- **不做**人才建档、简历解析（只校验 `talent_id` 存在）；
- **不做**岗位能力模型的维护（只读 `position_requirements`，标准由 HR / 岗位模块维护）；
- **不做**前端页面与推送渠道实现（只产生推送记录与事件，渠道由通知模块订阅）；
- **不做**课程内容生产（只匹配已有课程，缺课就明说）；
- **不做**培训 A/B 实验（单企业样本量不足，统计上不成立）。

## 11. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 方案里全是「外部学习方向建议」 | 课程库为空或维度名不一致 | 跑 `seed_training_courses.py`；核对 `courses.category` 与 gaps 维度 |
| 报「人才不存在」 | `talent_id` 无对应档案 | 先由人才模块建档，或跑 `demo_training.py` 造演示人才 |
| `generated_by` 一直是 `rule` | 未配 `LLM_API_KEY` | 正常行为（避免无效重试）；要 AI 排期就配 Key |
| 接口 500 且日志报 1452 外键 | 早期版本未做前置校验 | 已修：`create_plan` 先查人才，返回 404 而非 500 |
| pytest 报 `NoneType has no attribute 'send'` | Python 3.13 + aiomysql 跨事件循环复用连接 | 本模块测试已用 `NullPool` 隔离；公共层测试建议在 `mysql_ready` 后 dispose engine |
