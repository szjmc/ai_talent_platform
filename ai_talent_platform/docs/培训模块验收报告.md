## 三、本次发现并修复的 7 个缺陷

| # | 现象 | 根因 | 修复 | 回归用例 |
| --- | --- | --- | --- | --- |
| 1 | `POST /trainings/plans/{id}/score` **恒定 422**「plan_id: Field required」，接口完全不可用 | `ScoreSubmitRequest.plan_id` 设为必填，而路由是靠 `model_copy` 从**路径参数**注入的；FastAPI 在注入前已完成校验 | Schema 中 `plan_id` / `talent_id` 改为可缺省；Service 内解析并强校验 | `test_提交考核只给路径plan_id即可通过` |
| 2 | 用他人 `talent_id` 上报进度 → **500**（外键异常） | `update_progress` 未校验人才归属，直接按传入 `talent_id` 建记录 | 校验 `data.talent_id == plan.talent_id`，不一致返回 422 | `test_进度上报拒绝他人人才` |
| 3 | 上报**计划外课程**的进度 → 静默 200，脏数据入库 | 未校验课程是否属于该计划；记录写入后 `plan_courses` 里没有它 | 新增 `PlanCourseRepository.has_course()`，不属于计划直接 422 | `test_进度上报拒绝计划外课程` |
| 4 | 计划详情 `total_weeks` = **课程条数**（2 门课报 2 周），实际周期 4 周 | `len(plan.plan_courses)` 误当周数 | 按起止日期算周数（新增 `_weeks_between`）；同时把**排期周次**落进 `plan_courses.sort`，详情可还原「第几周上什么课」 | `test_计划详情周数按日期算而不是课程数` |
| 5 | 同一计划的 `total_hours`：生成接口 **15.0**、详情接口 **15.5** | 生成时用「排期学时」（skeleton 求和），详情用「课程实际学时」，而进度计算用的是后者 | 统一以落库课程学时为权威口径；排期学时任然可见，改为独立字段 `scheduled_hours` | `test_生成与详情的总学时一致` |
| 6 | **只读角色可越权写进度**：`EMPLOYEE` / `MANAGER` 只有 `training:read`，却能调 `POST /trainings/records` 给任意人才改进度 | 写接口误挂 `TRAINING_READ` 权限依赖 | 改为 `TRAINING_MANAGE`；读接口保持 `TRAINING_READ`（员工仍能看计划） | `test_只读角色不能写学习进度` |
| 7 | 并发上报同一记录 → **整单 500**（`IntegrityError` 撞唯一键） | `upsert` 先查后插，两个请求同时查不到就同时插入；唯一键 `uq_learning_records_plan_course_talent` 拒掉后到者。学员连点两次上报即可复现 | 插入包进 `SAVEPOINT`（`begin_nested`），撞键只回滚这一条并重查，退化为更新；外层事务不受影响 | `test_并发上报撞唯一键时退化为更新` |

### 附带修复（口径性缺陷）

**「学完」被写成「考过」**：`update_progress` 在 `progress >= 100` 时写入 `passed=True`，导致未参加考核的记录进入通过率分母且计为通过，通过率虚高。已完成率与通过率正是本模块反复强调要区分的两个指标（见 `PassRateStatsResponse` 注释与 `pass_rate_stats` 口径说明），现已改为只更新 `status`，通过结论只由节点 6 产生。

> 回归用例：`test_学满百分百只算完成不算通过`

### 修复影响面

- 新增测试文件 `tests/test_training_router.py`（9 条接口级回归用例）——此前 **`/score` 没有任何路由级测试**，这是缺陷 1 能长期潜伏的直接原因
- `scripts/selfcheck.py` 的 L4 层由「仅探针」升级为「接口回归用例 + 探针」，同类问题不会再漏检
- 新增手动冒烟脚本 `scripts/smoke_training_e2e.py`
- 修改文件：`app/schemas/training.py`、`app/services/training_service.py`、`app/repositories/training_repository.py`、`app/routers/training_router.py`、`app/ai/agents/training_logic.py`、`scripts/selfcheck.py`
- L1/L2 原有 44 条用例全部保持通过，无回归

> **前端要同步的一处行为变更**：`POST /trainings/records` 现在需要 `training:manage`。用 `admin` / `hr` 账号调用不受影响；如果用 `employee` / `manager` 账号在页面上报学习进度，会从原来的 200 变成 403。这是修复越权（缺陷 6）的必然结果——若产品要求学员自助上报，需要先做 `user → talent` 绑定与 `SELF` 数据范围，属迭代项。

### 一条「看起来像缺陷、实际是设计约束」的项

排查中发现：课程 `category` 与能力维度名只要差一个字（如 `需求分析能力` vs `需求分析`），排课就会静默降级为「平台暂无课程」。

一度想改成模糊匹配，但 `test_课程创建与维度一致性提醒` 的注释明确写道「这里用测试锁定行为」，路由 docstring 也写明了「必须一字不差」。**这是刻意选择：宁可降级，也不能凭相似度把课挂到错的维度上——错配的课比没课更误导学员。** 因此回退了模糊匹配，只补可观测性：排课降级时输出 `WARNING`，带上「疑似应为」与库内现有分类，运营可据此发现是「真没课」还是「课名写错了一个字」。真正的根治办法（建课时做维度字典校验并提示）属于迭代项，不擅自改变业务语义。

## 四、模块现有功能清单

### 4.1 六个节点（核心链路）

| 节点 | 能力 | 关键实现 |
| --- | --- | --- |
| 1 短板诊断 | 剔除已达标项、算缺口/优先级/预估学时；目标分与权重可来自**岗位能力模型**、调用方显式传入或默认值，并标注来源 | `diagnose` + `training_logic.diagnose_gaps` / `merge_requirement_model` |
| 2 方案排期 | 按优先级把学时塞进周次，每周限容量，单块限 4h；容量不足**显式报错**并建议周数，绝不静默丢学时；LLM 排期可介入，结构非法则回退规则 | `rule_schedule` / `legal_skeleton` / `merge_skeleton` |
| 3 课程匹配 | **课程实体只能来自课程库**：维度一致 → 未学过未占用 → 层级贴合 → 学时优先；库里无课则降级为「外部学习方向建议」，绝不编造课程名，并给出 `library_rate` | `match_courses` / `_pick_course` |
| 4 计划推送存档 | 落库（计划 + 计划课程 + 初始记录）、生成方案说明（LLM 失败回退模板）、发布 `training.plan.created` 事件 | `create_plan` |
| 5 进度跟踪 | 进度单调递增、学时/进度比反作弊（<30% 标记 `suspicious`）、按「时间进度 vs 完成学时」判定 正常/提醒/HR预警、定时扫描产出预警清单 | `update_progress` / `get_progress` / `scan_lag` |
| 6 考核复测 | 及格线 80 分判定、不通过发 `plan.adjust`、通过发 `retest.required` 回流测评 Agent；通过率统计（整体 + 按课程） | `submit_score` / `pass_rate` |

### 4.2 接口（11 条路径 / 13 个方法，全部挂 RBAC）

```
POST   /trainings/plans/generate        生成方案（节点 1~4）
GET    /trainings/plans                 计划列表（批量算完成率，无 N+1）
GET    /trainings/plans/{id}            计划详情（课表 + 溯源字段）
GET    /trainings/plans/{id}/progress   进度统计（节点 5）
POST   /trainings/plans/{id}/score      提交考核（节点 6）
GET    /trainings/stats/pass-rate       通过率统计
POST   /trainings/records               写回学习进度
POST   /trainings/lag-scan              滞后扫描（定时任务入口）
GET    /trainings/courses               课程列表
POST   /trainings/courses               新建课程（同名拒绝）
PUT    /trainings/courses/{id}          更新课程
DELETE /trainings/courses/{id}          下架课程（软删，保历史）
POST   /trainings/recommend             按短板推荐课程（不建计划）
```

### 4.3 数据模型（4 张表）

`courses`（19 门种子课程）/ `training_plans`（含 AI 生成标记与缺口来源测评 ID）/ `plan_courses`（复合主键 + 周次 + 是否必过）/ `learning_records`（进度、学时、分数、通过、反作弊标记）

### 4.4 设计上的三个亮点

1. **零 Key 可跑通**：`_llm_ready()` 判断无凭据时直接走规则排期，不会卡在 3 次重试 + 跨模型降级链上。
2. **降级可视**：`generated_by` / `summary_source` / `requirement_source` 三个溯源字段，前端能解释「这个方案是模型排的还是规则排的、标准来自岗位模型还是默认值」。
3. **跨模块只读**：通过 `TalentExistenceReader` / `PositionRequirementReader` / `AssessmentGapReader` 三个只读门面读别人的表，不改测评与岗位模块任何代码。

## 五、可迭代方向（按优先级）

### P0 · 补闭环缺口（当前有「断头路」）

| 方向 | 现状问题 | 建议做法 |
| --- | --- | --- |
| **复测闭环的消费方** | `training.retest.required` 事件已发出，但**没有订阅者**，闭环实际断在最后一步 | 测评 Agent 侧实现订阅：收到事件后自动创建复测测评单，回写分数后再触发新一轮 `diagnose` |
| **计划调整落地接口** | 考核不通过只发 `training.plan.adjust` 事件，没有「延长 2 周 / 换课 / 重排」的接口，HR 只能手工改库 | 新增 `POST /trainings/plans/{id}/adjust`（延长周期、替换课程、重算排期），复用 `rule_schedule` |
| **维度字典与课程校验** | `course.category` 必须与能力维度名一字不差，差一个字不报错、只静默降级为「无课可推」 | 建维度字典表；创建/更新课程时校验 category ∈ 字典；排课未命中时返回告警字段而非静默降级 |

### P1 · 提升业务真实度

| 方向 | 说明 |
| --- | --- |
| **排期与课程学时的对齐** | 现在先按缺口估 3~8h 再匹配固定学时课程，会出现「排期 8h / 课程 7.5h」的漂移（已由 `scheduled_hours` 暴露）。可让排期直接按候选课程学时反推，或细化到章节粒度 |
| **同维度多门递进组合** | `match_courses` 对同一维度只挑一门课并跨周复用。缺口大时应支持 L2→L3 两门递进，而不是把 8 小时全压在一门课上 |
| **外部学习任务实体化** | `is_platform=False` 的建议单元目前不落库，详情看不到、也不计学时。应建实体支持 HR 线下采购、回执与学时确认 |
| **反作弊升级** | 目前只看「学时/进度比 < 30%」。可加入进度跳跃频率、学习时段分布、并发设备、单次时长异常等特征，输出风险分而非布尔标记 |
| **排期约束增强** | 增加课程前置依赖（SQL 入门 → 优化）、同周课程数上限、避开考核周与节假日 |

### P1 · 工程健壮性

| 方向 | 说明 |
| --- | --- |
| **学员自助上报** | 越过权已修（接口从 `TRAINING_READ` 收回 `TRAINING_MANAGE`）。但 `EMPLOYEE` 现在还**不能**上报自己的进度——需要先建立 `user → talent` 绑定并接入数据范围 `SELF`，才谈得上「只能改自己」 |
| **幂等键** | 并发撞唯一键已修（SAVEPOINT 退化更新）。但同一请求重复提交仍会覆盖（进度单调递增能挡住回退，挡不住重复计数场景）。建议加 `Idempotency-Key` 与提交序列号 |
| **事件可靠性** | `event_bus.publish` 是进程内实现，重启即丢。建议落 outbox 表 + 异步投递 + 重试 |
| **内置调度** | `scan_lag` 依赖外部 cron 调接口，缺少失败重试与告警。可接 APScheduler 并记录每次扫描的覆盖与失败数 |
| **可观测性** | 补节点耗时、LLM 调用成功率、**降级率**（`generated_by=rule` 占比）等指标，答辩时能直接给出数字 |

### P2 · 产品体验

- **学员端视图**：「我的学习任务」列表 + 待办提醒（现在只有 HR 视角的计划与统计）
- **排期导出**：导出 ICS 日历 / Excel 课表，方便学员排时间
- **培训 ROI**：学时成本 vs 能力提升分的对比，以及部门完成率排名
- **课程评价**：学完后的满意度与难度反馈，回流优化 `_pick_course` 的层级贴合策略

## 六、边界说明（不属于本模块的问题）

### L3 回归层 4 条失败

```
tests/test_architecture_layer.py::test_vanna_model_uses_config_and_preserves_override[sql]
tests/test_architecture_layer.py::test_vanna_model_uses_config_and_preserves_override[summary]
tests/test_architecture_layer.py::test_vanna_compatible_endpoint_request[sql]
tests/test_architecture_layer.py::test_vanna_compatible_endpoint_request[summary]
```

**根因**：本机 `.env` 里 `LLM_PROVIDER=qwen` 但 `LLM_MODEL=deepseek-chat`（走 DeepSeek 的 OpenAI 兼容端点）。架构组 `model_selector.select_model()` 的第 3 步要求「LLM_MODEL 与供应商匹配且不是该供应商目录默认值」，deepseek-chat 不属于 qwen 目录，于是回落到按用途默认值 `qwen-plus` / `qwen-turbo`，与测试断言的 `settings.LLM_MODEL` 不等。

**归属**：架构组 `app/ai/core/model_selector.py` + 本机环境配置。

**两种解法**（择一）：
1. 把 `.env` 改为 `LLM_PROVIDER=openai`（DeepSeek 走 OpenAI 兼容端点），模型目录即匹配；
2. 架构组放宽 `select_model` 的目录校验，或在 `.env` 显式配置 `LLM_MODEL_MAP=default:deepseek-chat`。

> 培训模块不受影响：`training_agent._use_custom_endpoint()` 已识别自定义端点并走本模块专用客户端。
