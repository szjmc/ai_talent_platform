## P0-1 结课考核会把累计学习学时清零【已实证】

**位置**：`training_service.py:777-786` `submit_score`

```python
await self.repo.record.upsert(
    self.db, plan_id=plan_id, course_id=course_id, talent_id=talent_id,
    progress=100, study_minutes=0,        # ← 这里
    score=data.score, passed=result["passed"],
)
```

`upsert` 对 `study_minutes` 是**覆盖写**（`training_repository.py:427`）：

```python
if study_minutes is not None:
    record.study_minutes = int(study_minutes)
```

传 `0` 不是"不改"，而是"改成 0"。且 `submit_score` 遍历计划下**所有课程**，等于整份计划的学习时长归零。

**实测**（本地库，事务内验证后已回滚）：

```
考核前：study_minutes = 300 分钟
考核后：study_minutes = 0   分钟
进度判定：完成学时 0.0h / 落后 100% → HR预警
```

**影响链**：

1. 学员真实学习时长从统计中消失（`sum_minutes` = 0）
2. `GET /plans/{id}/progress` 永远返回"完成 0h、落后 100%"
3. 考核**未通过**时 `plan.status` 保持 `ongoing`，`lag-scan` 下次扫描会把这个刚学完 4 周的学员判成 **HR 预警**，并发出 `training.lag.alert`
4. 完成率不受影响（`progress=100`），所以"完成率 100% + 落后 100%"会同时出现在一个页面上，自相矛盾

**修复**：`submit_score` 去掉 `study_minutes=0` 参数即可（传 `None` 表示不改）。约 2 行改动，无行为副作用。

**为什么没被测试抓到**：现有用例只断言 `passed`、`progress`、`status`，没有一条断言"考核后学时保留"。

## P0-2 重复生成计划无任何防护【库内已有实例】

**位置**：`training_service.py:290` `create_plan` 每次 `TrainingPlan(...)` 新建

`POST /trainings/plans/generate` 无论调用多少次，都会为同一人才新增一份计划，没有"是否已有进行中计划"的判断。

**实测**：本地库 `talents.id=2` 下已存在 2 份完全同名的计划

```
2 份  人才2·数据分析等3项能力提升计划   ← id 11 / 13
1 份  张伟·数据分析等3项能力提升计划
1 份  张伟·需求分析等4项能力提升计划
```

这就是演示或联调时"点了几次生成方案"留下的。

**影响**：

- 计划列表出现同名重复项，HR 不知道该看哪一个
- 新计划的进度从 0 开始，同一门课在两条计划下各有一条学习记录，完成率各算各的
- `learned_course_ids` 只过滤 `progress>=100`，重复计划的 0 进度记录不影响排课，但会持续堆积

**修复建议**（需产品决策，不擅自改）：

- 方案 A：生成前查同人才 `status in (ongoing, draft)` 的计划，存在则返回 409 并提示"已有进行中计划"
- 方案 B：新增 `replace_existing: bool = False` 参数，为 `true` 时先软删旧计划再建
- `scripts/demo_training.py` 是自己先清理旧计划再跑，所以脚本演示看不出这个问题，只有走接口才会暴露

## P0-3 学员与主管都没有写权限，培训模块只有 HR 能操作

**位置**：`app/core/permissions.py:135-155`

| 角色 | training:read | training:manage |
|---|---|---|
| ADMIN | ✓ | ✓ |
| HR | ✓ | ✓ |
| MANAGER | ✓ | ✗ |
| EMPLOYEE | ✓ | ✗ |

而所有写接口都要求 `TRAINING_MANAGE`：生成计划、上报进度、提交考核、课程增删改、lag-scan。

**后果**：

- **员工无法上报自己的学习进度**（403）——培训的执行主体恰恰是员工本人
- **主管无法给下属提交考核**（403）——主管只能看，不能判
- 现实中退化成"HR 替全公司所有人打卡"

**这不是代码 bug，是设计缺口**，需要三件事配套：

1. `users` 与 `talents` 的绑定关系（当前两表无关联字段，无法判断"登录用户是哪个员工"）
2. 数据范围 `SELF`：员工只能操作自己的记录
3. 把 `POST /records` 的权限从 `TRAINING_MANAGE` 拆成"本人 or 管理者"两种放行逻辑

**答辩口径建议**：如果本期不做，就明确说"当前阶段由 HR 统一录入，员工自助端在下一迭代"，不要含糊成"已支持"。

## P1-1 事件全部空转：生产代码里没有任何订阅者

**实测**：全仓 `.subscribe(` 调用点只有 6 处，**全部在 `scripts/` 和 `tests/`**，`app/` 下零订阅。

事件总线在无订阅者时静默丢弃（`event_bus.py:100`）：

```python
if not handlers:
    logger.debug("事件 %s 无订阅者，忽略", event_name)
    return None
```

**受影响的承诺**：

| 事件 | 宣称的作用 | 实际 |
|---|---|---|
| `training.plan_created` | 推送计划给员工（`channels: ["inapp"]`） | 无人消费，`inapp` 无实现 |
| `training.lag.remind` | 落后 ≥20% 提醒 | 无人消费 |
| `training.lag.alert` | 落后 ≥40% 通知 HR | 无人消费 |
| `training.retest.required` | 回流测评 Agent 复测 | 无人消费，且测评模块**没有复测入口** |
| `training.plan.adjust` | 考核不通过调整计划 | 无人消费 |

补充：`app/services/` 下没有 notification / message 相关服务，全项目**没有推送通道实现**。

**结论**：节点 4 的"推送"、节点 6 的"复测回流"目前都只是"发出一个没人接的事件"。演示脚本自己订阅并打印，所以看起来是通的。

**建议**：要么补一个最小的 `notification_service`（订阅 4 个事件写站内信表），要么在交付说明里如实标注"事件已发出，消费方待对接"。**前者工作量不大，且能直接补上答辩的最大漏洞。**

## P1-2 三个培训事件没进统一事件注册表

`event_bus.py:47` 的 `ALL_EVENTS` 只登记了 `training.plan_created`，缺：

- `training.lag.alert`
- `training.lag.remind`
- `training.retest.required`
- `training.plan.adjust`

`ALL_EVENTS` 通常用于批量注册审计/日志订阅。将来一旦有人按它批量订阅，这 4 个事件会被漏掉。

**修复**：补进 `ALL_EVENTS`，并在 `training_logic.py` 里把它们提成常量（现在是散落的字符串字面量）。

## P1-3 查询接口有副作用：GET 进度会重复发预警事件

**位置**：`training_service.py:682-686`

```python
event = L.lag_event(progress["alert"], plan_id, progress)
if event and publish:
    event_bus.publish(event["type"], event)     # GET 请求里发事件
```

`GET /trainings/plans/{id}/progress` 每被调用一次就发一次事件，而 `lag_event` **没有任何去重或频率限制**。

**后果**：前端轮询、页面刷新、HR 多点几下，都会重复触发推送（一旦有了订阅者，就是重复轰炸）。

**修复**：GET 只算不推，推送交给 `POST /lag-scan`（定时任务）；或按 `plan_id + alert level + 日期` 做幂等键。

## P1-4 更新课程不校验重名

- `create_course` 查 `get_by_title`，重名抛 `BusinessRuleError`（有校验）
- `update_course` 直接把 `title` 写进去（**无校验**）

**后果**：可以把课程 B 改成与课程 A 同名。之后 `seed_training_courses.py` 按 title 匹配会命中 id 较小的那条，更新到错误的课程上。

**修复**：`update_course` 里如果 `title` 变了，先查重（排除自身 id）。

## P1-5 学习记录的 NULL 外键破坏唯一约束

**位置**：`models/training.py:176-186`

```python
plan_id   ... nullable=True, ForeignKey("training_plans.id", ondelete="SET NULL")
course_id ... nullable=True, ForeignKey("courses.id", ondelete="SET NULL")
UniqueConstraint("plan_id", "course_id", "talent_id", ...)
```

MySQL 的唯一索引对 `NULL` 不生效（`NULL != NULL`）。一旦计划或课程被物理删除，`SET NULL` 会把记录变成孤儿，此时唯一约束**完全失效**，可以无限插入重复记录。

而 `get_record` 用 `scalar_one_or_none()`：

```python
return (await db.execute(stmt)).scalar_one_or_none()   # 多行直接抛 MultipleResultsFound
```

**实测**：本地库 `learning_records` 39 条中有 **26 条 `plan_id IS NULL`**，且 `(course_id=3, talent_id=2)` 重复出现多次。之前跑验证脚本时，`get_record(plan_id=None, ...)` 直接抛 `MultipleResultsFound`。

**影响**：

- `list_progress_by_talent`（个人学习进度）会把这些孤儿记录一起返回，页面出现"不属于任何计划的课"
- 极端情况下 `get_record` 抛 500

**修复建议**：`plan_id` 改为 `nullable=False` + `ondelete="CASCADE"`（计划删了记录一起删），或在查询里强制 `plan_id.is_not(None)`。同时清理现有 26 条孤儿数据。

## 团队级问题（不属于培训模块，但影响它）

**数据范围（DataScope）全项目未生效。** `app/core/permissions.py` 定义了 `ROLE_DATA_SCOPE`，
但除 NL2SQL 的 `inject_data_scope` 外，没有任何业务接口应用它。

对培训模块的具体影响：MANAGER 只有 `training:read`，却能通过 `GET /plans` 看到**全公司所有人的培训计划**（含绩效敏感的考核分数）。这是越权读取。

建议上报架构组统一处理，不在培训模块单独打补丁。
