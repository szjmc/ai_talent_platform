# 人才档案模块：复用团队表结构版

本版撤回此前新增的4张业务表及任务队列，所有MySQL模型与团队原有25张表一致，不增加列、索引或迁移，不需要建表权限。公共鉴权、会话、LLMManager、分层及统一响应约定不变。

## 现有存储映射

| 内容 | 团队已有表/字段 |
| --- | --- |
| 原始文件元信息 | files，文件本体仍由公共存储适配器保存 |
| 简历、解析状态和失败原因 | resumes.status / parsed_data / parse_error / parsed_at |
| 人才主档及版本 | talents / talents.version |
| 画像、标签及版本 | talent_portraits |
| 合并前后脱敏资料和冲突处理 | audit_logs.before_data / after_data，action=update，module=talent |
| 文本向量和来源 | 沿用Milvus适配器；不建立MySQL索引状态表 |

parsed_data沿用本模块的JSON内容：parsed、warnings、source_pages、analysis_meta、duplicates。它们是已有JSON列内的数据键，不是新增数据库列。没有把任务或租约数据藏进其他业务字段。

## 启动

使用团队已有环境和数据库。需要补充Python包时参考requirements-talent.txt；业务参数参考.env.talent.example，不覆盖团队的数据库或登录配置。

只需团队原有Web启动方式：

```bash
python -m uvicorn main:app --reload
```

不执行init_talent_tables，不启动talent_worker；这两个此前提供的脚本已移除。未执行任何团队数据库DDL，也不会为满足模块运行而修改公共自动建表/启动逻辑。

对话模型、Embedding、Milvus、OCR依赖仍需配置。PDF文本层、DOCX、TXT可直接解析；图片和扫描件需Tesseract及语言包，旧版DOC需LibreOffice。工作年限未知时，原始解析保留null，但原有talents.work_years非空约束使主档沿用0，不应把这个0解释为已经证实没有经验。

## 请求方式变化

所有路径加团队公共前缀/api/v1，需使用有相应权限的登录账号。

1. POST /resumes/upload：单份上传，HTTP 201，返回resume_id；只保存文件。
2. POST /resumes/{resume_id}/parse：请求体可用{"force": false}，等待解析完成后HTTP 200返回结果，不再返回task_id。
3. POST /resumes/upload/batch：multipart的files字段接收多份文件，逐份上传并解析，HTTP 200返回total、accepted、rejected。accepted表示上传接收成功，不代表解析成功，必须检查accepted[i].result.status。
4. GET /resumes/{resume_id}/result：查看原表中的解析状态和结果。
5. POST /talents/{id}/portrait/refresh：请求内刷新画像并尝试同步向量，返回各阶段状态，HTTP 200。
6. POST /talents/{id}/index/refresh：请求内仅重新同步向量，HTTP 200。
7. 原来我额外提供的/resumes/tasks/...及/resumes/batches/...接口已移除，没有对应的持久化任务或批次。

解析结果：status沿用resumes的uploaded/parsing/success/failed；processing_status用于本次处理的succeeded/needs_review/failed。HTTP 200表示请求已处理，业务是否成功要看这些状态。解析失败使用保存点回滚解析阶段，将错误写入原有parse_error，保留已上传记录，可重新调用parse。批量请求最终由公共会话提交；请求中断、数据库故障导致外层事务回滚时，不能保证此前处理项已提交。

创建/修改/绑定/合并人才后，在请求内尝试生成画像和同步向量。响应中的refresh.portrait和refresh.index分别描述结果；AI故障会回滚该派生阶段并提示失败，正常情况下主档仍可保存。向量未启用时明确返回disabled。这里没有重启续跑、后台百分比进度或跨进程队列，失败后需重新请求。

## 向量查询与一致性

使用原有talents.version加文本内容摘要构造向量主键。搜索先按用户权限及当前版本过滤，再从现有档案、简历和画像表重建证据，核对分块主键，使用数据库中的正文返回结果。这样不会信任Milvus里过期或被篡改的正文，也无需索引状态表。

人才详情的index.status为not_checked；pending_count为null（未知），不将未命中误报为未索引。向量同步接口返回本次结果。MySQL与Milvus没有跨库事务：外部向量写入后MySQL若回滚，读取时会过滤不匹配的版本和内容。旧版本/已删除人才的向量暂时保留并被查询排除，统一清理由团队维护流程处理；本模块不删除整个集合。

Milvus集合仍按既有适配器契约工作。首次同步可能调用该适配器已有的幂等集合初始化；本次限制为不新增/修改MySQL表和字段。若向量集合也只允许管理员初始化，请由架构师提供兼容的现有集合名，勿删除团队集合。

## 手动验收顺序

先一份TXT：上传→解析→查看档案→查看画像→搜索→问答；再测试两个合法文件加一个错误文件的批量请求。最后测试：解析服务失败后文件仍能查询；主档修改而画像失败时响应有提示；合并记录进入audit_logs；修改/删除后旧向量不能成为有效证据。

本版不宣称99%准确率、无限量批处理或全程无需复核；复杂文档、模型效果及真实数据库联调由手动验收确认。原有技能/画像标签和引用约束保持，潜力及维度评分尚未有统一标准，不生成虚假评分。
