## 二、一调就崩的断点（已修）

### P0-1 人才向量链路整体失效：`MilvusAdapter` 被知识库实现覆盖

- **现象**：人才语义索引 / 语义搜索 / 档案问答全部不可用。
- **根因**：合并前 `MilvusAdapter` 是「一适配器一集合」的人才向量实现（`create_collection(name, dim)` / `upsert(collection, ids, vectors, metadata)` / `search(collection, vector, top_k, expr)`）。合并时被 RAG 组的 `knowledge_chunks` 固定 Schema 版覆盖，接口变成 `ensure_collection(dimension)` / `upsert(ids, vectors, doc_id, metadata)`。
  `TalentRetrievalService.sync_index` 调的 `create_collection` 根本不存在，`upsert` 参数含义完全不同，`metadata` 里也没有它要求的 `category`。
- **为什么没被发现**：唯一会暴露问题的 `tests/talent_agent/test_gxd_milvus.py` 默认 skip（需 `GXD_MILVUS_TEST=1`）。
- **修复**：新增 `app/adapters/vector_store/talent_vector_store.py`（`TalentVectorStore`，实现 `BaseVectorStore` 契约，`talent_vectors` 集合，`metadata` 用 JSON 字段以支持 `metadata["talent_id"] == 1` 过滤），`TalentRetrievalService` 改注入它；同时把 skip 用例改为打新适配器，并补一个离线契约用例（假 client 覆盖建集合幂等 / JSON 过滤 / 覆盖写 / 指定删除 / 维度校验）。

### P0-2 智能问答 `/text2answer` 每次请求 500

- **现象**：`POST /api/v1/text2answer` 与 `/conversations*` 必然报 `AttributeError`。
- **根因**：`MemoryService`（RAG/Agent 组）调 `ConversationRepository.owned / messages / append_turn`，而合并后的仓储只有架构组命名的 `get_by_session_key_or_id / get_recent_messages / append_message`。三处方法名全部对不上，连新会话都在第 36 行就崩。
- **修复**：在 `ConversationRepository` 补三个薄适配方法（复用既有实现，不复制业务逻辑），保留两套命名并存。

### P0-3 简历绑定人才 `POST /resumes/{id}/bind` 必然 500

- **根因**：`resume_service.bind` 调用 `TalentService.get_for_resume_binding(...)`，**该方法在合并后代码里完全不存在**（`grep` 全仓仅此一处调用）。
- **修复**：改为同栈既有 `get_detail(talent_id, current_user=user)`，同样做「存在性 + 数据行级范围」校验，语义等价。

### P0-4 简历解析文本提取用错字段，每次解析都失败

- **根因**：`talent_resume_service.source_text` 写 `d.content`，而 LangChain `Document` 的正文是 `page_content`。异常被工作流捕获后简历直接落 `failed`，日志只有一句「gxd-简历解析失败」。
- **修复**：改 `d.page_content` 并加注释说明。

### P1-5 两个简历技能指向了错误的服务

- **根因**：`ResumeParseSkill` / `ResumeDedupeSkill` 都 `import_dependency("app.services.resume_service", "ResumeService")` 并 `service_cls()` 无参构造。而那份 `ResumeService.__init__(self, db)` 必须传 db，且既没有 `parse_resume` 也没有 `dedupe_resume`（实现都在 `talent_resume_service`）。即使构造成功，`require_dependency` 也只会报「未就绪」。
- **修复**：改指 `talent_resume_service.ResumeService`，以 `service_cls(None, context=context)` 构造（传 `None` 时该服务自己开 `session_scope`），`requires` 声明同步纠正。

### P1-6 `FileService` 两个同名 `read`，后者覆盖前者

- **根因**：第 90 行 `read(file_id)`（简历场景，返回 `(file, bytes)`）被第 145 行 `read(record)`（通用对象读取）覆盖 → 调用方传 int 时报 `'int' object has no attribute 'storage_type'`。
- **修复**：后者改名 `read_object(record)`，更新 6 个调用方（知识库 / 文件中心 / 简历），docstring 里写清分工。

   - `app.openapi()` 生成 + `operationId` 唯一性校验（拦重复注册）
