图 1 · 一次 HTTP 请求的完整数据链路

从客户端到 MySQL 再回到客户端：13 个步骤，3 条横切能力（trace_id / 事务 / 权限）。

  • 中间件只做横切（trace / 跨域 / 日志 / 安全头 / 限流），不做鉴权与业务。
  • 鉴权发生在「依赖解析」这一步：get_current_user → require_permission。
  • Repository 不 commit；事务由 get_db() 在响应发送前统一提交或回滚。

图 2 · 中间件的注册顺序与执行顺序

Starlette 把「后注册」放在最外层：注册顺序与执行顺序整体相反。

  • 执行顺序：TraceId → CORS → AccessLog → SecurityHeaders → RateLimit → ExceptionMiddleware。
  • TraceId 最外层，保证预检、限流拒绝、404/401 的日志也带 trace_id。
  • 限流是进程内实现，多实例部署需换 Redis（incr_with_ttl）。

图 3 · 登录鉴权时序

bcrypt 校验 → 失败计数 / 锁定 → 双令牌签发 → 角色与权限码下发。

  • 密码错误与用户不存在返回同一个错误（2003），防止账号枚举。
  • access_token 默认 1 天；remember_me=True 时改用 7 天。refresh_token 固定 7 天且不轮转。
  • 失败计数存在「写库后抛异常被回滚」的陷阱，需显式提交（见手册 5.5）。

图 4 · 每个请求的鉴权与权限决策路径

认证（Authentication）→ 功能权限（RBAC）→ 数据范围（Data Scope）三级防线。

  • Token 中的 roles 仅用于展示与审计；鉴权以数据库 role_codes 为准，改角色立即生效。
  • 依赖缓存保证同一请求只查一次用户，鉴权与业务共享同一个 Session。
  • 401 与 403 语义不同：401 刷新令牌，403 不应重试。

图 5 · 数据库会话与事务边界

get_db() 的生成器生命周期：正常 commit、异常 rollback；以及局部事务与死锁重试。

  • 一个请求 = 一个 AsyncSession = 一个事务；成功路径的 commit 在响应发出之后（失败时客户端已是 2xx）。
  • 异常路径的 rollback 在错误响应之前；跨仓库原子操作使用 transaction()（SAVEPOINT）。
  • 陷阱：先写库再抛业务异常 → 写入被回滚（登录失败计数需独立事务提交）。

图 6 · 公共组件地图与调用方向

全平台横切能力的唯一入口，业务代码不要重复造轮子。

  • 调用方向单向：routers → services → repositories → infrastructure。
  • core/* 与 utils/* 可被任意层引用；AI 与 adapters 只允许在 Service 层调用。
  • 可选依赖（Redis / Milvus / PgSQL / LLM）未启用时必须自动降级。

图 7 · AI 对话链路与事件总线

AgentService → AIContext → dispatch → BaseAgent → LLMManager → 适配器；Skill 与 EventBus 的定位。

  • 身份与权限只从 AIContext / 数据库读取，模型传入的 user_id / roles 一律不可信。
  • Agent 与 Skill 禁止裸 SQL、禁止直接操作 ORM，只能调用公开 Service / Repository / 适配器。
  • 外部能力必须可降级：未启用时抛明确异常，不允许静默返回空答案。
对应代码：app/core/（中间件 / 鉴权 / 响应 / 异常）、app/infrastructure/（会话 / 事务 / 缓存 / 事件）、 app/repositories/（数据访问）、app/ai/（AI 公共层）。 详细说明与代码示例见 数据链路与鉴权实现手册。
