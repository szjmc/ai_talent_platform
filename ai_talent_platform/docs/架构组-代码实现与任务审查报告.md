## 2. 统一日志实现思路（逐层拆解）

### 2.1 组件构成

```
                      ┌──────────────────────────────────────────┐
  请求 ──▶ TraceIdMiddleware  → trace_id_ctx.set(uuid/请求头)      │ app/core/middleware.py:43
                      │        request.state.trace_id             │
                      ▼                                          │
          AccessLogMiddleware  → 计时 + 状态码 + IP + 慢请求告警    │ app/core/middleware.py:60
                      ▼                                          │
          SecurityHeadersMiddleware / CORS / RateLimit            │
                      ▼                                          │
          Router → Service → Repository                          │
                      │  任意层 logger.info(...)                  │
                      ▼                                          │
          logging 根 Logger → TraceIdFilter 注入 trace_id         │ app/config/logging_config.py:34
                      ├─▶ StreamHandler(stdout)
                      └─▶ RotatingFileHandler(logs/app.log, 20MB×10)
                      ▼                                          │
          异常 → exception_handlers（统一 api_response + 日志）      │ app/core/exception_handlers.py:48
                      ▼
          ApiResponse.trace_id = trace_id_ctx.get()               │ app/core/response.py:70
```

### 2.2 关键实现

**a) 日志规范（`app/config/logging_config.py`）**

- 格式固定：`%(asctime)s | %(levelname)-7s | %(trace_id)s | %(name)s | %(message)s`（第 30 行），四级信息即可定位"哪个请求、哪个模块、什么错"。
- `trace_id_ctx: ContextVar[str]`（第 28 行）默认 `"-"`，保证脚本/后台任务里日志格式不炸。
- `TraceIdFilter`（第 34 行）在每条日志落盘前读取 contextvar 注入 `record.trace_id`，因此**业务代码不需要手动传 trace_id**。
- `setup_logging()`（第 45 行）用 `_configured` 做幂等，可被 `lifespan` 与 `main.py` 重复调用；同时把 `uvicorn.access`、`aiomysql`、`sqlalchemy.engine.Engine` 收敛到 `WARNING`，避免访问日志重复。
- `get_logger()`（第 83 行）未初始化时自动兜底 `setup_logging()`，这是"新模块忘记初始化也不会丢日志"的关键设计。

**b) 链路追踪（`app/core/middleware.py:43-57`）**

```python
trace_id = request.headers.get("X-Trace-Id") or uuid.uuid4().hex[:16]
token = trace_id_ctx.set(trace_id)
request.state.trace_id = trace_id
try:
    response = await call_next(request)
finally:
    trace_id_ctx.reset(token)      # 必须 reset，否则协程复用会串号
response.headers["X-Trace-Id"] = trace_id
```

- 优先复用上游网关传入的 `X-Trace-Id`，实现跨服务串联；无则本地生成 16 位 hex。
- 回写响应头，前端报错截图即可直接拿到 trace_id。
- 中间件注册顺序（第 145-164 行）符合 Starlette 语义：**后 `add_middleware` 先执行**，因此 trace_id 最后注册、最先执行，保证其余中间件日志都带 trace_id。

**c) 访问日志与慢请求（第 60-88 行）**

- `time.perf_counter()` 计时，`>=1000ms` 自动升级为 `logger.warning`，无需额外配置慢查询阈值。
- IP 解析优先 `X-Forwarded-For` 第一段，兼容反向代理。
- 回写 `X-Process-Time-Ms`，前端可在 Network 面板直接看到服务端耗时。

**d) 异常日志分级（`app/core/exception_handlers.py`）**

| 异常类型 | 日志级别 | 是否打堆栈 | 对外响应 |
| --- | --- | --- | --- |
| `BusinessException` | `warning` | 否 | `code/message` 取自异常，HTTP 同源 |
| `RequestValidationError` | `warning` | 否 | 422 + `[{field, message, type}]` |
| `StarletteHTTPException` | 不记录 | 否 | 包装为统一结构（404 → "接口不存在"） |
| 其它 `Exception` | `error` (`logger.exception`) | 是 | 500 + "系统繁忙，请稍后重试"（隐藏细节） |

这个分级是正确做法：业务异常是预期内分支，打堆栈只会淹没真正的故障。

**e) 统一响应携带 trace_id（`app/core/response.py:62-107`）**

`ApiResponse.success/error/api_response` 均从 `trace_id_ctx` 取值填入 `trace_id` 字段，**日志与响应体共用同一个 ID**，这是排查闭环的关键。

### 2.3 用法

```python
# 推荐
from app.config.logging_config import get_logger
logger = get_logger(__name__)
logger.info("创建用户 id=%s username=%s", user.id, user.username)   # 参数化，禁止 f-string 拼接

# 兼容入口（给习惯旧路径的同学，实现在同一处）

```

### 2.4 日志侧缺陷

| 级别 | 问题 | 位置 | 说明与建议 |
| --- | --- | --- | --- |
| P1 | 多 worker 下 `RotatingFileHandler` 轮转不安全 | `logging_config.py:65-73` | 4 个 uvicorn worker 同时写并轮转 `app.log` 会出现竞态（Windows 上直接 PermissionError）。生产建议改为 stdout + 外部采集（Filebeat/Loki），或按 pid 分文件 |
| P1 | 无敏感字段脱敏 | 全局 | 访问日志仅记 path，但 `?token=xxx` 类查询串会原样落盘；`AuditService` 设计有脱敏但未实现。建议在 formatter 层统一正则脱敏 |
| P1 | `trace_id` 未做合法性校验 | `middleware.py:49` | 直接信任请求头，攻击者可注入换行/超长串污染日志。建议 `re.fullmatch(r"[A-Za-z0-9-]{6,64}")` 校验后再用 |
| P2 | 无结构化日志（JSON） | 全局 | 目前是纯文本，无法按字段检索（如"所有 cost>1s 且 status=500 的请求"）。建议新增 JSON formatter 开关 |
| P2 | 异常日志重复 | `exception_handlers.py:54` + `middleware.py:78` | 业务异常会先被 AccessLog 记一次，再被 handler 记一次，量为 2 倍。可将 access 日志降为 `debug` 或对 4xx 跳过 |
| P2 | 无"请求体/响应体"审计级日志 | 全局 | 合规场景需要"谁改了什么"，需靠审计表而非日志，本项与第 3.6 节合并解决 |

## 3. 权限管控实现思路

权限体系实际由**三套独立机制**拼成，评审时必须分开看，否则容易误判"权限已做完"。

```
机制 A：接口级 RBAC（已落地，可用）
  JWT → get_current_user → require_permission(PermissionEnum.X) → 403/2004

机制 B：行级数据范围 DataScope（只写了纯函数，未接入）
  get_data_scope(roles) → all/dept_sub/dept/self → check_data_scope(...)

机制 C：AI 侧权限（依赖 AIContext，但 AIContext 无注入点，实际失效）
  set_context(user) → get_context() → SkillContext.roles → BaseSkill._check_permission
```

### 3.1 机制 A：接口级 RBAC

**a) 权限模型（`app/core/permissions.py`）**

- 5 个内置角色：`super_admin / admin / hr / manager / employee`（第 34 行）。
- **28 个权限码**，命名规范 `模块:动作`（第 44-79 行），覆盖用户/组织/人才/岗位/简历/测评/培训/匹配/知识/分析/Agent/文件/审计。
- 角色→权限矩阵 `ROLE_PERMISSIONS`（第 92 行）为**代码内静态字典**；`super_admin` 持有通配符 `"*"`。
- 判定函数全部为纯函数：`has_permission` / `has_any_permission` / `has_all_permissions` / `check_permission`，便于在 Service、Skill、Agent 任意层复用。

**b) 认证凭据（`app/core/security.py`）**

| 项 | 实现 |
| --- | --- |
| 密码 | bcrypt（`BCRYPT_ROUNDS=12` 可配）；>72 字节先 sha256 压缩，规避 bcrypt 上限（第 39-44 行） |
| 校验容错 | `verify_password` 捕获 `ValueError/TypeError` 返回 `False`，脏哈希不会把登录接口打成 500（第 61-63 行） |
| 访问令牌 | PyJWT HS256，payload 含 `sub/type/iat/exp/jti`，默认 1440 分钟 |
| 刷新令牌 | 独立 `type=refresh`，7 天，`decode_token(expected_type="refresh")` 强校验类型，防"用 access 换 access" |
| 解析 | `options={"require": ["exp","sub"]}` 强制过期与主体存在；过期抛 `TokenExpiredError(2002)`，其它抛 `AuthError(2001)` |

**c) 依赖注入（`app/core/dependencies.py`）**

```python
bearer_scheme = HTTPBearer(auto_error=False)      # 关键：不抛框架 403，交给自己抛 2001

async def get_current_user(credentials, db) -> User:
    payload = decode_token(credentials.credentials)     # 1) 验签 + 过期 + 类型
    user = await UserRepository().get_by_id(db, int(payload["sub"]))  # 2) 查库
    if user is None or user.is_deleted: raise AuthError(...)           # 3) 存在性
    if not user.is_active: raise AccountDisabledError(2005)           # 4) 禁用
    if user.is_locked:     raise AccountLockedError(2006)             # 5) 锁定
    return user
```

设计要点（值得在评审中强调）：

- **权限以数据库角色为准，不以 Token 内 roles 为准**。`require_permission` 读的是 `user.role_codes`（来自 `roles` 关系的 `lazy="selectin"` 预加载），因此管理员改角色后**立即生效**，无需等 Token 过期。Token 里的 roles 只作为冗余信息。
- 依赖别名 `CurrentUser` / `DbSession` / `OptionalUser` 降低了 Router 样板代码。
- `require_permission(*perms, require_all=False)` 支持多权限；**默认是 OR 语义**，`require_all=True` 才是 AND。

**d) 接口覆盖（实测统计）**

| 路由 | 接口数 | 权限挂载 |
| --- | --- | --- |
| `auth_router` | 6 | 公开 3（register/login/refresh，`openapi_extra.security=[]`）；登录态 3 |
| `user_router` | 8 | `user:read` ×2、`user:create`、`user:update` ×3、`user:delete` |
| `organization_router` | 7 | `organization:read` ×3、`organization:manage` ×4 |

21 个接口全部显式挂载，无遗漏（用 `dependencies=[Depends(require_permission(...))]` 形式，不侵入函数签名）。

**e) 业务层二次防护（做得好的地方）**

`UserService` 在权限码之外还做了对象级校验，这类校验无法用注解表达，必须写在 Service：

- `set_status`：不能改自己（`BusinessRuleError`）、不能禁用超管（`PermissionDeniedError`）（第 140-144 行）
- `delete_user`：不能删自己、不能删超管，且逻辑删除时把 `username` 改写为 `username#deleted#<id>`、清空 `mobile/email`，**释放唯一键占用**（第 165-183 行）
- `OrganizationService.move_org`：目标不能是自己或自己的子孙（用 `path` 前缀判定，第 156-159 行），移动后级联重写子孙 `path/level`

**f) 登录防爆破（`app/services/auth_service.py:88-128`）**

失败不区分"用户不存在/密码错误"（统一 `CredentialsError(2003)`，防用户名枚举）；失败累计 `fail_count`，达 `LOGIN_MAX_FAIL_TIMES=5` 写入 `locked_until=now+15min` 并清零计数；成功则清零并记录 `last_login_at/ip`。

### 3.2 机制 B：行级数据范围（未落地）

```python
# permissions.py:198
def get_data_scope(roles) -> str:
    priority = [ALL, DEPT_SUB, DEPT, SELF]      # 多角色取最宽
    ...

# permissions.py:208
def check_data_scope(roles, *, owner_id, current_user_id, dept_in_scope=True) -> None:
    scope = get_data_scope(roles)
    if scope == ALL: return
    if scope == SELF and owner_id != current_user_id: raise PermissionDeniedError("无权访问他人数据")
    if not dept_in_scope: raise PermissionDeniedError("无权访问其他部门数据")
```

问题在于：

- `ROLE_DATA_SCOPE` 中 `manager → dept_sub`、`employee → self`，语义已定义；
- 但 `UserService.page_list` 只按请求传入的 `organization_id` 过滤，**没有注入当前用户的 scope 条件**；
- 因此一个 `manager` 调用 `GET /users` 仍能翻到全公司用户。这是"接口级权限通过、行级权限失效"的典型漏洞。

**修复模式建议**（写在 Service，不写在 Router）：

```python
scope = get_data_scope(operator.role_codes)
if scope in (DataScopeEnum.DEPT, DataScopeEnum.DEPT_SUB):
    org_ids = await org_repo.subtree_ids(db, operator.organization_id) if scope == DEPT_SUB else [operator.organization_id]
    filters["organization_id"] = org_ids          # BaseRepository 支持 list → IN 查询
elif scope == DataScopeEnum.SELF:
    filters["id"] = operator.id
```

`BaseRepository._apply_filters`（`repositories/base.py:76-91`）已支持 `list/tuple/set → column.in_()`，因此接入成本极低，主要是"每张表要有归属字段（`organization_id` / `created_by`）"这一前提。

### 3.3 机制 C：AI 侧权限（设计正确、装配缺失）

**设计**（`app/ai/context.py`）：

```python
@dataclass
class AIContext:
    user_id, username, roles, organization_id, trace_id, conversation_id, extra
    data_scope  -> get_data_scope(roles)
    has_permission(code) / require_permission(code)

set_context(user, **extra) -> AIContext     # 从 User 对象映射 roles/org
get_context() -> AIContext                  # 未设置返回 ANONYMOUS_CONTEXT，不抛异常
clear_context() / context_scope() / async_context_scope()
```

**Skill 侧强制规则**（`app/ai/skills/base.py:311-320`）：

```python
def _check_permission(self, context: SkillContext):
    if not self.required_permission: return
    if has_permission(context.roles, self.required_permission): return
    raise PermissionDeniedError(f"当前角色无权使用该技能（需要 {self.required_permission}）")
```

这是正确的安全姿态——**身份只从上下文取，忽略 LLM 传入的任何 user_id/roles 参数**，防止提示词注入提权。

**但存在断点**：全仓除 `context.py` 自身外，`set_context` 调用数为 **0**。

```
影响链：
无 set_context
  → get_context() 永远返回 ANONYMOUS_CONTEXT（roles=[]）
  → SkillContext.roles = []
  → has_permission([], "matching:read") == False
  → 8 个 Skill（均声明了 required_permission）调用必然 403/2004
```

此外 `AgentService`（`app/services/agent_service.py:50`）仍是骨架，尚未承担"注入上下文"的职责。**这是当前 AI 链路事实上不可用的根因，优先级最高。**

**修复位置建议**（二者选一，推荐第一种）：

1. 中间件级：在 `get_current_user` 成功后 `set_context(user)`，请求结束 `clear_context()`（放在 `TraceIdMiddleware` 的 `finally` 里最省事，但拿不到 user）；更稳的是在 `dependencies.py` 里做一层"认证即建上下文"的依赖。
2. 服务级：`AgentService.chat/task` 入口 `with context_scope(user):`，适合后台任务与脚本显式重建。

### 3.4 权限设计层面的三个结构性建议

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 权限存储 | `ROLE_PERMISSIONS` 硬编码在 Python | `roles` 表已存在但无权限字段；建议增加 `role_permissions` 表 + 启动时加载到内存缓存，否则"新增权限/调整授权"必须改代码发版 |
| 默认语义 | `require_permission` 默认 OR | 多权限场景误用概率高；建议对多权限强制显式传 `require_all`，或在 docstring 标注高风险 |

### 4.3 数据库与事务

| 组件 | 文件 | 要点 |
| --- | --- | --- |
| MySQL 引擎 | `infrastructure/database/mysql.py` | 连接池 `pool_size=10 / max_overflow=20 / pool_recycle=3600 / pool_pre_ping=True`，`autocommit=False` 显式事务 |
| 请求会话 | `session.py:61` `get_db()` | **一请求一事务**：`yield` 后 commit，异常 rollback 并重新抛出（交给全局 handler） |
| 后台会话 | `session.py:79` `session_scope()` | 脚本/定时任务/后台 Agent 用，语义同 `get_db` |
| 显式事务 | `transaction.py:55` | 已在事务中 → `begin_nested()`（SAVEPOINT）；否则 `begin()` |

**用法**

```python
# Router
async def endpoint(db: AsyncSession = Depends(get_db)): ...

# 后台 / Skill（无请求上下文）

    ...

# 局部事务

    ...
```

**架构级风险（P1）**：`get_db` 的事务边界是"整个请求"。而 `dispatch()` 的默认超时是 `settings.LLM_TIMEOUT=60s`（`ai/agent.py:119`）。这意味着**一次 AI 调用会在持有数据库连接与事务的情况下阻塞最长 60 秒**，并发上来会直接打满 `pool_size=10`。建议：

- 进入 AI 调用前 `await db.commit()` 提前释放事务（读操作可 `await db.close()` 换新会话）；
- 或为 AI 链路单独使用 `session_scope()`，与请求事务解耦。

### 4.4 ORM 与通用仓储

**`app/models/base.py`**

- `Base`：`DeclarativeBase` + 统一 `NAMING_CONVENTION`（索引/约束名可预测，方便 Alembic）。
- `BaseModel = Base + TimestampMixin + SoftDeleteMixin + OperatorMixin`，另加 `id: BigInteger` 与 `version: int`（乐观锁，默认 1）。
- `soft_delete()` / `restore()` 语义清晰，删除只置标记与时间。

**`app/repositories/base.py`（17 个方法，全平台数据访问唯一底座）**

```python
class TalentRepository(BaseRepository[Talent]):
    model = Talent
    filterable_fields = {"education", "status", "organization_id"}   # 精确筛选白名单
    searchable_fields = {"name", "phone"}                            # 模糊搜索字段
    sortable_fields   = {"created_at", "name"}                       # 排序白名单
```

三个白名单是关键安全设计：

- `_apply_filters` 只接受白名单字段，未知字段**静默忽略**（防注入/防越权筛选）；
- `_apply_order` 非法字段回退 `default_order`，且排序追加主键保证分页稳定（第 126-129 行）；
- `_apply_keyword` 多字段 `OR LIKE`，仅限 `searchable_fields`。

**已发现的 Bug（P0）**：`_flush_with_unique_guard`（第 399-407 行）与 `create_many`（第 322-326 行）在捕获 `IntegrityError` 后执行 `await db.rollback()`。由于它们运行在 `get_db` 的请求事务内，`rollback()` 会把**本请求此前所有写入一并回滚**，随后 `get_db` 的 `commit()` 变成空提交——表现为"接口返回 409，但用户刚提交的其他数据也没了"。

修复建议（二选一）：

```python
# 方案 A：savepoint（推荐，保留前序写入）
async with db.begin_nested():
    await db.flush()

# 方案 B：只 flush 不 rollback，交由上层事务统一回滚
try:
    await db.flush()
except IntegrityError as exc:
    raise DuplicateError(...) from exc
```

**实现时必须注意的两个坑**

1. `AuditService.log()` **不能复用请求会话**。审计事件在 `publish` 时是 `create_task` 异步执行的，此时请求会话可能已 commit/close。必须内部 `async with session_scope() as db:` 独立会话（这也是 `session_scope` 存在的意义）。
2. `FileService` 的 `db` 必须是 `AsyncSession | None`（任务书明确要求）。`file_skill`/`resume_skill` 会无参构造并反射调用，`None` 时内部自建会话；否则 RAG 组无法调用。

## 9. 给评审会的三条结论

1. **底座质量可以打高分，但"已冻结"的表述需要收窄**。日志、响应、异常、事务、BaseRepository、认证三个样板模块确实达到了"其余组照抄即可"的水准；而文件中心、审计、行级权限三项属于"设计已定、实现未落地"，文档应明确标注，避免其他组按"已可用"去对接。

2. **当前最高优先级不是加功能，而是修三个"静默失效"**：`AIContext` 未注入（AI 权限失效）、DataScope 未接入（行级权限失效）、审计未入库（合规失效）。这三项的共同特点是"代码看起来有、实际不生效"，比缺功能更危险。

3. **跨组契约要先于业务代码冻结**。`FileService` 的方法签名（尤其 `db: AsyncSession | None`）和 `file_utils` 的真实函数名，是 RAG 组、Vanna 组开工的前置条件；建议本周内先提交这 4 个文件的最小可用版本（哪怕不含孤儿清理），解除两个组的阻塞。
