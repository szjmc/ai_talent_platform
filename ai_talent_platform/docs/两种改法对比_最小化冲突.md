# 两种改法对比：合并前最小化冲突方案

> 生成时间：2026-11-06
> 目标：合并 `origin/develop` 前，先改我方 `test_merge_lz_xh` 代码，让冲突最小化，同时**保留我方 3 块功能**（继任方案 / 周期报告 / 员工脱敏）
> 状态：**仅分析，未改任何代码**

---

## 一、关键事实（已确认）

1. **我方 3 块功能在 develop 里一个都没有**，不存在"撞车"：
   - 继任方案（succession）→ develop 无（只有一句文案）
   - 周期报告（period_report）→ develop 无
   - 员工脱敏（desensitize）→ develop 无
   - 6 个独有新文件（`succession_service` / `succession_rules` / `report_cache` / `desensitize` / `analytics_agent` / `analytics_repository`）→ develop 全无，合并时直接保留

2. **冲突根源**：develop 把我方功能依赖的"地基"重构了：
   - `agent_service.chat()` 从 `chat(agent_type, payload, user)` 重写为 `chat(body: AgentChatRequest, current_user)`，内部走 `run_supervisor`（LangGraph）+ Dify 分支，不再支持"analytics + report_type"的确定性调用
   - `agent_router.py` 整份重构，新增 SSE 流式/会话/任务接口
   - `middleware.py` 大改（限流/trace_id/CORS）

3. **两个接口的依赖差异（决定解耦点）**：
   - `/succession`（继任方案）：**完全不依赖 chat**，直接调 `SuccessionService().generate()`，纯规则引擎 → 几乎可原样保留
   - `/report/period`（周期报告）：**依赖旧版 chat**，靠 `service.chat("analytics", {"report_type":...})` 调度 → 这是唯一需要解耦的
   - 周期报告真正的入口是 `analysis_workflow.run_analysis(question, data_scope, max_rows, report_type)`，**router 可直接调用，无需经过 agent_service**

---

## 二、两种改法对比

### 方案 A：解耦——报告接口独立直调（推荐）

**核心思路**：让 `/report/period` 和 `/succession` 直接调 `run_analysis` / `SuccessionService`，彻底绕开 `agent_service.chat()`。这样我方和 develop 在 `agent_service.py` 上**零冲突**。

**具体改动**：

| 文件 | 改什么 | 冲突结果 |
|------|--------|---------|
| `app/core/middleware.py` | 放弃我方 CORS 改动（develop 已覆盖） | ✅ 零冲突 |
| `app/services/agent_service.py` | **完全不动我方代码，合并时直接采用 develop 版** | ✅ 零冲突 |
| `app/routers/agent_router.py` | 以 develop 版为底，**追加** `/report/period`、`/succession` 两个接口；`/report/period` 内部改为直接调 `run_analysis`（不经过 service.chat） | 🟡 追加两段，冲突小 |
| `app/routers/router.py` | include 取并集 + 清 develop 重复键 bug | 🟡 手工合并 |
| `app/ai/workflows/analysis_workflow.py` | 保留两边函数（我方 `PERIOD_REPORT_TEMPLATE`/`run_analysis` + develop 分析函数） | 🟡 手工合并 |
| 员工脱敏 | 从 `agent_service.chat` 里拿出来，挂到 `/report/period`、`/succession` 的 router 返回出口（或独立小函数） | ✅ 跟随我方接口走 |

**优点**：
- 冲突最小，`agent_service.py` 这个最严重冲突直接归零
- 我方报告功能与 develop 的 LLM 对话架构彻底解耦，互不影响
- 逻辑更清晰：报告是"规则引擎确定性产物"，本就不该走"对话"

**缺点**：
- 周期报告原来靠 chat 里注入的 `set_context`/配额检查，解耦后需要**自己在 router 里补 `set_context(user)`**（一行）和权限（已有 require_roles）
- 需要确认 `run_analysis` 的 `data_scope` 参数从哪拿（原来从 user 角色算，解耦后要显式传）

---

### 方案 B：共存——保留两个 chat 方法

**核心思路**：保留我方旧版 `chat(agent_type, payload, user)` 作为独立方法，与 develop 新版 `chat(body, current_user)` 并存。

**具体改动**：

| 文件 | 改什么 | 冲突结果 |
|------|--------|---------|
| `app/core/middleware.py` | 放弃我方 CORS 改动 | ✅ 零冲突 |
| `app/services/agent_service.py` | 把 develop 版整体拿过来，**再加回**我方旧版 `chat()` 改名为 `chat_legacy()` 或 `run_report()` | 🔴 仍需手工合并（在 develop 基础上追加方法） |
| `app/routers/agent_router.py` | 以 develop 版为底，追加 `/report/period`、`/succession`，其中 `/report/period` 调 `service.run_report()` | 🟡 追加 |
| `app/routers/router.py` | include 并集 + 清 bug | 🟡 手工合并 |
| `app/ai/workflows/analysis_workflow.py` | 保留两边函数 | 🟡 手工合并 |

**优点**：
- 保留原有 `chat → dispatch` 调度链路，周期报告改动最小（只改个方法名）
- 员工脱敏逻辑可以继续挂在旧 chat 里

**缺点**：
- `agent_service.py` 仍然要手工合并（在 develop 的 625 行新代码里追加旧方法），冲突没真正消除
- 服务层出现两个 chat 方法，语义混乱，后续维护易混
- 我方旧 chat 依赖的 `dispatch(agent_type, payload)` 是否还被 develop 版 `app/ai/agent.py` 保留？需确认（develop 可能改成 `dispatch_stream`/`run_supervisor` 了）

## 三、方案对比总结

| 对比项 | 方案 A 解耦 | 方案 B 共存 |
|--------|------------|------------|
| agent_service.py 冲突 | ✅ 归零 | 🔴 仍要合并 |
| 改动量 | 中（router 里补 set_context + 直调 run_analysis） | 中（改方法名） |
| 架构清晰度 | ✅ 高（报告独立于对话） | ❌ 低（两个 chat） |
| 依赖风险 | 需确认 run_analysis 的 data_scope 来源 | 需确认 develop 是否保留 dispatch |
| 长期维护 | ✅ 好 | ❌ 差 |

**我的推荐：方案 A（解耦）**。理由：
1. 冲突最小（最严重文件归零）
2. 架构更合理——继任/周期报告是规则引擎产物，本就不该混进 LLM 对话
3. 你的 3 块功能完整保留，只是调度方式从"复用 chat"改成"直接调规则引擎"
