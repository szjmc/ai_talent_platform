# 人才数据决策 Agent · 接口数据流转文档

> 生成时间：2026-11-06 ｜ 核心思想：**「传进什么 → 干了什么 → 传出什么」**
> 本文档按接口逐条梳理数据流转，标注每一层（Router → Service → Agent/Workflow → 取数）的职责。

---

## 〇、总体分层架构

```
前端 HTML（Agent板块演示前端.html）
        ↓ HTTP
Router 层（agent_router.py）      → 参数校验、权限校验、调 Service
        ↓
Service 层（agent_service.py / succession_service.py）  → 编排业务
        ↓
调度器（ai/agent.py dispatch）    → 按 agent_type 派发到具体 Agent
        ↓
Agent 层（analytics_agent.py）    → build_prompt / parse_output
        ↓
Workflow 层（analysis_workflow.py）→ 取数 + 出图 + 风险规则 + 拼提示词
        ↓
取数层（sql_skill → Vanna NL2SQL / Repository → PgSQL）
```

**核心原则**：数字由「写死规则」算（不靠 LLM 算数），LLM 只做「业务推理 + 文字表达」，缺数据不编造。

## 一、POST `/agents/chat`（生成报告 / 单次分析）

### 数据流转

```
【传进】{ agent_type:"analytics", question:"帮我生成人才决策报告", conversation_id?:null }
    ↓
① Router：校验权限(AGENT_USE) → 调 AgentService.chat()
    ↓
② Service：set_context(user) 建立请求上下文 → dispatch("analytics", payload)
    ↓
③ Agent.build_prompt：
   - 读权限档 data_scope（从 context，不手动透传）
   - 调 run_analysis(question, data_scope)  → 取数 + 出图 + 风险 + 拼提示词
   - 取不到数据 → answered=False 拒答，不调 LLM（防幻觉）
   - 取到数据 → 触发第二次 LLM 业务推理 → 产出 report_meta
   - 成功 → 给基座「透传占位」prompt（第三次 LLM 几乎不干活）
   - 失败 → 降级走旧版 prompt
    ↓
④ Workflow.run_analysis 内部五步：
   collect_data（Vanna NL2SQL 查库）
     → build_charts（数据驱动出图）
     → detect_risks（14 条写死规则算风险，LLM 只补文字）
     → build_insight_prompt（拼业务推理提示词）
     → build_report（组装）
    ↓
⑤ Agent.parse_output：解析 LLM 返回的结构化 JSON
   - 优先用第二次产出的 report_meta
   - 容错解析 conclusions/risk_list/suggestions/meta/charts 等
    ↓
【传出】{ answered, conclusions[3条], risk_list[4条], charts[7张], meta{盘点用途/数据截止/数据范围/警戒线/目标}, key_talent_top3, appendix_note, ... }
```

### 关键点

- **两次 LLM 调用**：第 1 次是基座形式调用，第 2 次是真正的业务推理（`_build_business_meta`）。真实业务判断只来自第 2 次。
- **防幻觉闸门**：`run_analysis` 里 `has_data` 为 False 时直接拒答，不进 LLM。
- **风险数字由规则算**：`detect_risks` 用写死阈值算风险，LLM 只补充 `business_impact` 文字。

## 二、POST `/agents/report/period`（周期报告：周/月/年）

### 数据流转

```
【传进】{ report_type:"weekly" }   ← 注意：无 question，系统定时触发
    ↓
① Router：校验 report_type ∈ {weekly, monthly, yearly}
   - 非法 → ParamError(1001)，不走 Agent
    ↓
② Service.chat → dispatch("analytics", {report_type})
    ↓
③ Agent.build_prompt：
   - report_type 合法 → 走固定模板分支
   - question 为空正常（取数走固定查询清单 QUERY_GROUP_MAP）
   - 用周期标签生成占位 question（仅报告标识，不参与取数）
    ↓
④ Workflow.run_analysis：
   - 取数清单固定（QUERY_GROUP_MAP，与用户输入无关）
   - build_insight_prompt 注入周期叙事模板（PERIOD_REPORT_TEMPLATE）
     · weekly：执行层，6 板块
     · monthly：管理层，7 板块
     · yearly：战略层，7 板块
   - 占位板块（缺数据）要求 LLM 写「需接入数据后启用」，不编数字
    ↓
⑤ parse_output：透出 report_type + period_label
    ↓
【传出】{ report_type, period_label:"2026年第45周", conclusions[6条], risk_list, charts, ... }
```

### 关键点

- **与 chat 的本质区别**：周期报告**固定模板、系统定时触发**，不接受用户自然语言提问。
- **同一条数据三种切法**：周报盯变化、月报对目标、年报看资产，数据来源相同，叙事角度不同。
- **占位板块零编造**：缺数据的板块标注「需接入数据后启用」，不写假数字。

## 三、POST `/agents/succession`（继任方案）

### 数据流转

```
【传进】{ post_name:"研发负责人" }
    ↓
① Router：校验权限 → 调 SuccessionService.generate()
    ↓
② Service（不经过 Agent，纯规则，不调 LLM）：
   ① checked_scope 校验权限（必须 data_scope=all）
   ② 查 dim_talent_wide（匹配分 match_avg_score / 潜力 potential_level / 年限 work_years）
   ③ 查 fact_assessment_history 算「测评达标率」（优秀+良好占比）
   ④ 定「现任」：匹配分≥90 且 年限≥7 中匹配分最高者
   ⑤ 其余人作候选，喂给 succession_rules.build_succession_report
    ↓
③ 规则引擎 succession_rules.py（纯函数，可解释）：
   calc_readiness  算准备度 = 匹配分×40% + 潜力×30% + 经验×20% + 测评×10%
   grade_readiness 分级（≥85 可立即接任 / 70~84 培养后可接 / <70 长期储备）
   assess_risk     判空缺风险（0个→高 / 1个→中 / ≥2个→低）
   build_actions   生成建议动作（P0/P1，每条带 reason）
   build_succession_report 组装 + 记录 generated_at 时间戳
    ↓
【传出】{ post_name, generated_at, incumbent, risk, candidates[按准备度排序], qualified_count, actions }
```

### 关键点

- **不经过 LLM**：全程写死公式 + 阈值，可解释、可复现，避免数学幻觉。
- **数据实时查库**：每次请求实时查询 + 实时重算，`generated_at` 标注快照时刻。
- **「现任」用规则兜底**：数据库暂无「在任岗位」标记，用「匹配分最高 + 年限≥7」识别。

## 五、POST `/analytics/nl2sql`（智能问答，复用 Vanna 组）

```
【传进】{ question:"测评平均分是多少", with_insight:true }
    ↓
Vanna 组内部：NL2SQL 生成 SQL → 查库 → 返回数据 + insight
    ↓
【传出】{ columns, rows, insight_detail{summary/anomalies/causes/risks/suggestions}, insight(拼好的纯文本) }
```

**本组用法**：前端只取 `insight` 字段（后端 `vanna_adapter.py` 已拼好一段纯文本总结），不拆 `insight_detail` 渲染卡片。

## 六、GET `/analytics/assessment/summary`（测评统计）

```
【传进】无
    ↓
Vanna/Repository 聚合测评历史表
    ↓
【传出】{ record_count, scored_count, talent_count, average_score, minimum_score, maximum_score, source, basis }
```

**本组用法**：前端 `loadKpi()` 曾用它兜底「测评均分」，现已改为从报告 `charts` 直接取数（保证徽章与正文一致）。

## 七、数据来源表（核心字段 → 表）

| 字段 | 来源表 | 用途 |
|---|---|---|
| match_avg_score | dim_talent_wide | 继任匹配分（40% 权重） |
| potential_level | dim_talent_wide | 潜力等级（高/中/低，30% 权重） |
| work_years | dim_talent_wide | 工作年限（20% 权重） |
| level / total_score | fact_assessment_history | 测评达标率（优秀+良好占比，10% 权重） |
| name | dim_talent_wide | 人才姓名 |

## 八、一句话总结各接口

| 接口 | 一句话数据流 |
|---|---|
| /agents/chat | 用户提问 → 取数 → 规则算风险 → LLM 推理 → 结构化报告 |
| /agents/report/period | 固定模板 → 固定取数 → LLM 按周期叙事 → 分层报告 |
| /agents/succession | 查库 → 规则公式算准备度 → 判风险 → 建议动作 |
| GET /agents | 占位，空列表 |
| /analytics/nl2sql | 自然语言 → SQL → 数据 + 文字解读 |
| /analytics/assessment/summary | 测评表聚合 → 统计指标 |
